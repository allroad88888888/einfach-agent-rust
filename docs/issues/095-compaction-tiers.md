# 095 压缩分级与「存的 / 发的」分界（决策）

**里程碑** M12 · **依赖** 无 · **模型** opus · **独立测试 agent** 决策类不派 · **状态** 完成（2026-08-10 拍板）

## 目标

定压缩这件事的**形状**：分几档、每档改什么、状态字段长什么样、undo 怎么撤。

不定它就不能动手——`SendPlan` 的字段定错，后面 099–110 十四条全要返工。
「什么时候触发哪一档」是**另一条**，见 [096](096-compaction-trigger.md)；
这里只管形状，不管时机。

## 为什么要重定一次（决策 18 不够用）

[决策 18](../ROADMAP.md)「压缩三分」定的是分工：触发在 core（纯算术）、实现在 core
（走 command 层进 undo log）、压后摆盘在 adapter。这三条**继续成立，不推翻**。

但它底下压着一个没写出来的假设：**压缩会用摘要替换历史**。
ROADMAP §四那条「压缩与 undo 的窗口对立（P3）」就是这个假设的直接后果——
`prev` 要装下被替换的整段历史，`ExtensionOnly` 的家又逼着你压得又晚又狠，
单条 entry 巨大，cap 100 条（`history/cap.rs`）撑不住。

**这个假设可以拆掉**：完整对话记录本来就在库里（`SessionStore`），压缩没有理由去动它。
一旦压缩只发生在**发送侧**，「窗口对立」不是被折中掉，是不成立了。

## 要定的

### 1. 五档分级

压缩不是一个动作，是五个，按「丢失的不可逆程度」排：

| 档 | 做什么 | 丢的能拿回来吗 | 靠什么算出来 | 现状 |
|---|---|---|---|---|
| 1 进门截断 | 工具输出产生时就切 | 能（重跑） | 规则 | **已有**：`agent-core/src/limits.rs` |
| 2 清工具返回 | 老的 `tool_result` 不发 | 能（重跑） | 规则 | 无 |
| 3 摘要 | 一段历史换成一句摘要 | **不能** | **模型调用** | 无 |
| 4 清窗口 | 边界推到最新 | 能（记录还在） | 用户动作 | 无 |
| 5 子 agent | 中间过程不进父上下文 | 不能，但本来也不要 | 结构 | **已有**（M7/M8） |

**倾向：五档全要。** 3 是唯一需要模型调用、唯一不可重算的一档，所以它必须最后开火
（时机见 096），但不能没有——1/2 救不了「聊了三百轮，工具返回全清光还是超」。

### 2. 存的 / 发的分界

**倾向：完整对话记录一律入库，永不压缩；压缩只改「这一轮发什么」。**

于是：

- `SessionStore` / `History` 那条链**一个字节都不动**，`drop_oldest`、`drop_after`、
  快照压实的语义全部维持原样（那是空间管理，跟上下文压缩是两件事，别混）
- 审计回放走完整记录，压根不读压缩状态
- 崩溃恢复恢复的是完整记录 + 压缩状态两样，各自独立

### 3. `SendPlan` 三字段

发送侧要发什么，由一个纯值决定：

| 字段 | 装什么 | 谁改 |
|---|---|---|
| 已清列表 | 被清掉的 `ToolCallId` | 第 2 档 |
| 边界 | 从第几条开始发 | 第 3、4 档 |
| 摘要引用 | 边界之前那段的摘要在哪 | 第 3 档 |

三条约束：

- **容器禁 `HashMap`/`HashSet`**（红线 11）——它进 prompt，迭代顺序必须逐字节确定。
  用 `Vec` 或 `BTreeSet`。
- **摘要存引用不存正文**（红线 5）——正文是大值，`Arc` 包住放别处，`SendPlan` 里只有 id。
  这跟图片 `ms://` 存引用不存字节是同一个招（[IMAGES.md](../IMAGES.md) §四）。
- **投影必须是纯函数**（红线 1）——`(完整历史, SendPlan) → 要发的历史`，
  零 IO、零时钟、零随机，同一份输入投影一千次逐字节相同。

### 4. 压缩 entry 的 `prev` 形状

**倾向：只装边界值与引用，绝不装被替换的历史正文。**

一次压缩的 undo 记录长这样：

```
边界:     0 → 47
摘要引用: None → Some(摘要id)
```

两个数。序列化后 < 1KB，cap 100 条随便吃。

**这条是本 issue 的全部价值**——它一成立，「压缩与 undo 的窗口对立」当场消失，
不需要在「compact 视为不可逆边界」和「压缩前历史单独存一份」之间二选一，
因为完整历史**从来就没被动过**。

### 5. undo 语义

**倾向：压缩跟任何别的状态变更一模一样，没有特权，也不设屏障。**

- 撤销一次压缩 = 边界推回去、引用清掉，原文一个字没动
- 摘要正文留在库里不回收（下次压缩可能又要它；而且回收会让 redo 拿不回来）
- **压缩不是 undo 屏障**——`shell/exec` 那种真的动了外部世界的才需要屏障，
  压缩连内部状态都没动，凭什么拦

### 6. 决策 18 怎么处置

**倾向：不删，三分原样保留，只是「实现」那一档的内容变了。**

- 触发在 core：不变（纯算术，见 096）
- 实现在 core：不变，但从「生成摘要替换历史」变成「改 `SendPlan` 三个字段」
- 摆盘在 adapter：不变（adapter 仍然无权改世界，它只是按投影后的历史组装）

拍板后往 ROADMAP §三补一条决策号，并把 §四那条「压缩与 undo 的窗口对立（P3）」
划掉，注明被本 issue 化解——**理由要写清楚，不然半年后有人会照着旧假设重新纠结一遍**。

## 验收

决策类，产出是文档 + 后续 issue 的形状。可判定的三条：

- 任一档压缩后 `/undo` 一次，完整对话记录**逐字节**回到压缩前
- 压缩 entry 的 `prev` 序列化 < 1KB，且**不含任何被替换的历史正文**
- 审计回放只读完整记录，全程不读 `SendPlan`——把 `SendPlan` 整个清空，回放结果不变

## 注意

会踩的红线：

- **红线 1**（derived 纯函数）——投影是纯函数，这是它能不进 undo log 的前提
- **红线 2**（禁 `store.set()`）——`SendPlan` 的三个字段都是状态，一律走 command 层
- **红线 3**（primitive 可序列化）——`SendPlan` 要能进快照
- **红线 5**（大值 `Arc`）——摘要正文
- **红线 11**（序列化逐字节确定）——`SendPlan` 进 prompt，禁 `HashMap`/`HashSet`

另有一条不在红线里但同级的：**`tool_use` 与 `tool_result` 必须成对处理**。
只清 result 留着 use，有的 provider 直接 400。形状上体现为已清列表存的是
`ToolCallId` 而不是消息下标——按 id 才配得成对。

## 决策记录（2026-08-10 拍板）

**用户直接拍板一条**（第 5 点），其余五点按上面的倾向定，理由已在各节写明。

### 5. 压缩**不是** undo 屏障 —— 用户拍板

压缩之后照样能一路撤回去。理由：完整对话记录一直在 `SessionStore` 里，
压缩根本没动它，没有任何东西「已经发生且收不回来」。真正需要屏障的是
`shell/exec` 那类动了外部世界的操作。

**这条把 ROADMAP §四「压缩与 undo 的窗口对立（P3）」正式化解**——不是在
「compact 视为不可逆边界」和「压缩前历史单独存一份」里选一个，是这个问题
建立在「压缩会替换历史」的假设上，而该假设已被第 2 点拆掉。

### 1–4、6：按倾向定，无异议

- **1 五档全要**。第 3 档（摘要）用户明确要求保留——1/2 救不了「聊三百轮，
  工具结果全清光还是超」。
- **2 完整记录永不压缩，压缩只改发送侧**。
- **3 三字段**（已清列表 / 边界 / 摘要引用）。
- **4 压缩 entry 的 `prev` 只装边界值与引用**，不装被替换的正文。
- **6 决策 18 三分原样保留**，只是「实现」那一档从「生成摘要替换历史」变成
  「改 `SendPlan` 三个字段」。

2、3、4 三条已由 [099](099-send-plan.md) 落地兑现（`prev` < 1KB、投影纯函数、
`SendPlan` 三字段），不再是纸面决策。

### 落地时对本文的一处修正

099 定接口时读了 `value/message.rs` 才发现：**`ToolUse` / `ToolResult` 是
`Message.blocks` 里的块，不是独立消息**。于是「清工具返回」改成
**把 `ToolResult.content` 换成固定占位、`ToolUse` 块原样保留**，
而不是本文「注意」一节原设想的「成对删除」。

**「注意」最后那条硬约束（只清一半会让 provider 400）因此降级为历史记录**
——换占位的做法下配对天然不破，不需要靠「按 id 存而不按下标存」小心维护。
详见 [099](099-send-plan.md) §定死的接口。
