## 实做记录（2026-08-13）

**初稿在 `scratchpad/183-draft-en.md`。**

### 开篇没用「我做了实测」，用的是「文档两个方向都错」

原计划的开篇是「为什么要实测：三家都自称 OpenAI 兼容，文档说的和实际返回的不一样」。
写的时候发现素材里有更硬的东西——**不是「文档不全」，是文档在两个相反方向上都错**：

- DeepSeek 文档说 `tool_choice` 四种全支持，实际两种直接 400
- GLM 文档说只支持 `auto`，实际四种全支持

**「两个方向」才是关键**：如果错误方向一致，读者还能施加一个统一的修正；两个方向都错
就意味着文档整体不可作为依据。而且两种错法的后果不同——按 DeepSeek 文档写会崩，
按 GLM 文档写会白白降级，**两个都会看起来像你自己的 bug**。这一段现在是全文的地基。

### 三条主线，按「读者会付出什么代价」排

不按「缓存 / 工具 / 流式」这种素材本身的结构排，那是给写的人方便不是给读的人方便。
改成按后果排：

1. **改变你架构的那条**——缓存匹配语义分两类（GLM 真前缀树 vs 另两家仅扩展）。
   它决定「兄弟 agent 共享前缀」这条设计成不成立（只在 GLM 成立），
   也决定压缩一次值多少钱（**DeepSeek 上约等于 120 轮命中**）
2. **会静默搞坏你的那条**——Kimi 的 usage 在 finish 之后另起一帧且 `choices` 为空。
   假定每帧都有 `choices[0]` 的解码器**大概率不是 panic 而是静默丢掉 usage**，
   然后一切看起来正常，而所有缓存兜底从此失明
3. **反直觉的那条**——DeepSeek 上「追加一条 system 消息」把缓存清零（哪怕插入点之前
   逐字节相同），而「改写顶层 system」反而保住缓存。跟另两家完全相反

第 2 条写成了全文的价值主张：**「响得大声的失败是便宜的，一边正常工作一边悄悄
关掉你的仪表盘的才是贵的」**——这也正是本仓红线摘要那套判据，对外讲比对内更有说服力。

### 两个方法论细节留在了文章里

它们比结论更可迁移，所以没删：

- **「归零」不是「作废」**：冷轮 0% 曾被我误读成「改工具表把缓存打掉了」，
  复跑第二轮全部命中才发现旧前缀一直在，0 只是「这个变体第一次见」。
  **两种情况给出同一个数字，含义完全不同。**
- **测「听不听」必须给够 `max_tokens`**：DeepSeek 那次差点被判「未听」，
  实际是默认开着思考、314 token 全进了 reasoning、正文被截成空串。
  **不然你测的是截断，却当成了行为。**

### 数字核对

抽查了 11 个关键数字（5440 / 96.7% / 5276→5382 / 5120 / 3968 / 4352 / 194 / 191 /
640 / 2304），**每一个都在 `probes/PROVIDERS.md` 里有出处**，原始观测在
`probes/results/*.json`（五个文件都在）。文章结尾显式邀请读者复跑并报告差异
——数字会变，方法才是留下来的东西。
