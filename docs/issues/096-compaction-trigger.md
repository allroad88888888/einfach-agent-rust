# 096 触发策略：什么时候按哪一档（决策）

**里程碑** M12 · **依赖** [095](095-compaction-tiers.md) · **模型** opus · **独立测试 agent** 决策类不派 · **状态** 完成（2026-08-10 拍板）

## 目标

095 定了压缩长什么样，这条定**什么时候按哪一个按钮**。

两条落地：微观部分（水位、保护区、顺序）在 102，宏观部分（哪档先上、何时判、
谁不参与）在 108。这里不写代码。

## 为什么单独一条

它跟 095 是两种错误：095 定错了形状不对，返工；**096 定错了功能完全正常，只是每一轮
都全价**。后者是本仓最贵的那类 bug（红线 11 同款），值得单独拿出来定。

ROADMAP §四把「阈值取多少」记成 P3 未决，本 issue 连同它一起结掉。

## 要定的（七问）

### 一、拿什么数当「现在用了多少」

**倾向：只用上一轮实测的 `TokenUsage.prompt`，接受滞后一轮。**

本轮要发多少，发出去之前算不准。想算准就得估 token——那是模型相关知识，
写进 core 当场破红线 12。滞后一轮的代价是「本轮可能就爆了」，
那由 098 的单轮超窗兜底接住，不该由这里解决。

`SessionConfig.context_window` 为 `None`（未知/不设限）时**不触发任何一档**，
不许 `unwrap`（`value/session.rs:21` 的注释已经写了）。

### 二、每档一条线，还是只有一条线

**倾向：第 2 档看百分比，第 3 档不看百分比。**

- 第 2 档（清工具返回）：`prompt / context_window` 超过触发线 → 开火
- 第 3 档（摘要）：触发条件是「**第 2 档已经清光了还不够**」

第 3 档用状态条件而不是阈值条件，好处有二：少一个魔法数字；
语义正好等于要的阶梯——**便宜的招用尽才动贵的**。

### 三、⚠️ 一次压到什么水位（漏了这条会很贵）

**倾向：必须有滞回带。触发线 X%，压到目标线 Y%，Y 明显小于 X。**

如果压到「刚好低于线」，下一轮加两条消息又超了 → 又触发 → 又改中段 →
**每轮全价**。在 DeepSeek 上一次压缩值 ~120 轮的缓存钱（[PROVIDERS.md](../../probes/PROVIDERS.md) §一），
每轮触发是灾难，而且症状只在账单上浮出来，测试全绿。

**定为 X=85%、Y=30%**（Y 由用户拍板，见决策记录），数值待
[110](110-compaction-dogfood.md) 真机校准。两个值都可配置，默认值写明理由
（照 [004](004-tool-result-limit.md) 的做法）。

**修订（同日用户提出，收）**：第 2 档**没有目标水位**——它的动作是
「把最近 N 轮之前的工具结果**一次全清**」，够得着的就那些，清完为止。
于是 **Y 不再是第 2 档的停止条件，只剩一个用途：清完之后仍在 Y 以上，
才轮到第 3 档**。少一个魔法数字，而且缓冲效果是白捡的——清完之后要等新的
工具结果累积到超出保护区才有东西可清，不需要靠 Y 人为制造间隔。

这条顺带解决了第五问：一次清一大批比分五次各清一点便宜得多——
一次性代价 vs 五次一次性代价。

### 四、⚠️ 什么绝对不能碰

四条保护区，前两条是硬约束：

1. ~~**`tool_use` 与 `tool_result` 必须成对清**~~ —— **已被 [099](099-send-plan.md)
   的做法消解**：清除是把 `ToolResult.content` 换成固定占位、`ToolUse` 块原样保留，
   配对天然不破，不存在「只清一半让 provider 400」这条路。102 仍要验
   「投影后两边 id 集合恒等」，但那是回归锁，不是这里要防的风险。
2. **当前这一轮的工具返回不能清**（正在用）。
3. **最近 N 轮不动**。清了近期上下文等于自断手脚，模型会开始重复已经做过的事。
   N 取多少一并定，倾向 3。
4. **用户消息永远不进第 2 档**。第 2 档只吃 `tool_result`；用户说过的话归第 3 档管
   ——那才是唯一有权改写用户输入的一档，而且它改完还留着原文。

### 五、同一档内先清谁

**「一次全清」之后这不再是选择题**——够得着的全清，没有「先清谁」。

只剩一件事：**已清列表的排列顺序按最老优先**。它不影响清哪些，只影响
`SendPlan` 序列化出来的字节序——而那必须逐字节确定（红线 11）。
按历史顺序排是唯一跟输入天然对齐、不需要额外记账的排法。

### 六、在哪个时间点判

**倾向：turn 结束拿到 usage 时判，下一轮出料单时生效。**

输入是已经落定的实测值，于是**同一份历史重放两次必然做出同样的压缩决定**——
跟 `cache/window.rs` 那条「按轮计数不按时间」是同一个道理（红线 1 的精神）。

发请求前判的话，输入里必然混进「这轮打算发什么」的估计值，重放就不确定了。

### 七、哪几档不参与自动阶梯

要写死，不然以后有人往里加：

- **第 1 档（截断）常开**，不看压力，跟这个阶梯无关
- **第 4 档（清窗口）是用户动作**，不受阈值管
- **第 5 档（子 agent）是结构性的**，编排时就定了，运行时不触发

**自动阶梯里只有 2 和 3 两档。**

### 八、用户主动触发的两个按钮（同日补，用户提出）

跟自动阶梯并行存在，**不受 X / Y 任何一个约束**：

| 按钮 | 动作 | 留最近 N 轮？ |
|---|---|---|
| **主动摘要** | 边界推到「最近 N 轮之前」，那一段全摘，**压到多长算多长** | **留** |
| **清窗口**（第 4 档） | 边界推到最新，不生成摘要 | **不留** |

**主动摘要留最近 N 轮**，理由跟第四问的保护区一样：把近期也摘掉，模型会断片、
原地重做刚做过的事。用户按「压缩」是想接着干活，不是想失忆。

**清窗口不留**——用户要的就是干净开始，还给他留三轮不是他要的。
想留就该按另一个按钮。两个按钮语义必须分开，别合成一个带参数的。

**主动摘要没有目标水位**（用户原话「模型自己压到多少算多少」）：水位是自动档
用来决定「够不够、要不要继续」的东西；用户按下去就是执行一次，没有「够了没」
这个问题。

## 验收

决策类，落地验收挂在 102 和 108 上：

- **102**：造一个稳定增长的会话跑 30 轮，第 2 档触发次数 **≤ 2**；每次触发后，
  **最近 3 轮之外的工具结果一个不剩**（「一次全清」的字面验收）、最近 3 轮的
  **一个没动**；投影后 `ToolUse` 与 `ToolResult` 的 id 集合恒等；
  `context_window: None` 时一次都不触发且不 panic
- **102 · 反向锁**：第 2 档**不是常开**——用量在 X 以下时，哪怕有大量够得着的
  工具结果也一次都不触发。漏了这条会变成每轮改中段、每轮全价，而测试全绿
- **108**：造一个「清工具返回够用」的场景，第 3 档**一次都没触发**（零模型调用）；
  同一份历史重放两次，压缩决定逐字节相同
- **110**（真机）：**每一次第 3 档开火之前，第 2 档已经把可清的都清光了**
  ——与工作负载无关的真不变量。原来那条「第 3 档触发次数 ≤ 第 2 档的 1/3」
  在 Y=30 下可能永远达不到（见决策记录第三问的连带效应），已废弃

## 注意

- **红线 1**——触发判读必须是纯函数，按轮不按时间，否则重放不确定
- **红线 12**——触发只做算术，不许出现 `match provider`，也不许 `if caps.xxx()`。
  这正是决策 17 化解掉 `compaction_cost_multiple()` 的地方（[ADAPTER.md](../ADAPTER.md) §五个能力位）：
  按窗口压力触发，不看折扣比
- 第 2、3 档都要在触发那轮把 `PrefixIntent` 置成 `Intentional`（103），
  不然缓存兜底第 1 层会把预期内的漂移报成事故，**压一次报一次假警报，
  然后人开始无视这一层**（`cache/drift.rs:21` 的注释就是为这天写的）

## 决策记录（2026-08-10 拍板）

**用户直接拍板一条**（第三问的目标水位），其余六问按倾向定。

### 三、水位：85% 触发；第 2 档一次全清，Y=30 只当第 3 档的闸 —— 用户拍板

原建议「压到 60%」，用户先定 **30%**，随后又提出更好的做法：
**第 2 档不设目标水位，直接把最近 N 轮之前的工具结果一次全清**。两条一起收。

先说 30% 这个数为什么好：

85→30 的缓冲比 85→60 大一倍多，每次压完能多撑 **约 2.2 倍**的轮数，压缩事件数
砍掉一半以上。而压缩的主要代价是那一轮的**全价重编码**（DeepSeek 上一次
≈120 轮命中的钱，[PROVIDERS.md](../../probes/PROVIDERS.md) §一），事件数减半就是直接省钱。

**连带效应，必须记下来**：要从 85% 降到 30% 得腾出 55% 的窗口。工具结果占不到
55% 时，光靠第 2 档够不着 30%，**必须上第 3 档**。所以第 3 档开火的频率跟工作
负载强相关：

| 工作负载 | 工具结果占比 | 第 3 档 |
|---|---|---|
| 工具重（大量读文件 / 搜代码） | 大 | 清完可能直接掉到 30% 以下，不开火 |
| 聊天重 | 小 | 清光了仍在 50%，**每次都开火** |

这不改变「先清工具结果，不够才摘要」的顺序，但
**[110](110-compaction-dogfood.md) 原来那条验收「第 3 档触发次数 ≤ 第 2 档的 1/3」
在 Y=30 下可能永远达不到**，已改成与负载无关的真不变量：
**每次第 3 档开火前，第 2 档必须已经清光**。

摘要那次模型调用本身可以走便宜模型（[106](106-summary-via-subagent.md) 用
`ChildConfig` 指定），所以「第 3 档更常开火」的钱是可控的；全价重编码不可控，
省它才是主要矛盾。

**再说「一次全清」为什么比「清到 Y 为止」好**（用户提出，收）：

- 「清到 Y 为止」需要 Y 当停止条件，那是个魔法数字；「一次全清」的停止条件是
  「够得着的清完了」，不需要数字
- 缓冲效果**白捡**：清完之后要等新的工具结果累积到超出「最近 N 轮」保护区
  才有东西可清，天然稀疏，不必靠 Y 人为制造间隔
- 每次清除都要付一轮全价重编码，所以「能清多少清多少」本来就是最优解——
  留一半下次再清 = 多付一次全价

于是 **Y=30 降级**：不再是第 2 档的目标，只剩「清完仍在 30% 以上才轮到第 3 档」
这一个用途。

**但第 2 档绝不能改成常开。** 「最近 N 轮」这条线每轮都在往前挪，常开的话每轮
都有新的工具结果被清 → 每轮中段都变 → **每轮全价**。必须是压力触发（到 X 才
动手）+ 单调（清过的不因为后来宽松了又放回来）。102 为此加了一条反向锁验收。

### 一、二、四、五、六、七：按倾向定，无异议

- **一** 只用上一轮实测 `TokenUsage.prompt`，接受滞后一轮；`context_window: None`
  不触发。滞后那一轮爆掉由 [098](098-single-turn-overflow.md) 接住。
- **二** 第 2 档看百分比，第 3 档看状态条件（「第 2 档清光了还不够」）。
- **四** 保护区，**最近 N = 3 轮**。原第 1 条（成对清）已被 099 的做法消解。
- **五** 最老优先。
- **六** turn 结束拿到 usage 时判，下一轮出料单时生效。
- **七** 自动阶梯里只有第 2、3 档。

### ⚠️ 落地时的一处澄清（[108](108-tier-ladder.md) 定接口时发现）

**「压到 Y=30%」没法作为停止条件实现**：压之前算不出压之后是多少 token，
要算得有 tokenizer——那是模型相关知识，写进 core 当场破红线 12
（[004](004-tool-result-limit.md) 也早写过「字节数和 token 数关系不稳定」）。

同理，**「第 2 档清完还不够」也没法在同一轮里判**。所以阶梯是**时间上的**：
这一轮清工具结果，下一轮再实测；还超就说明清不动了，那时第 2 档自然返回空，
第 3 档接手。**一轮的代价换一个不用猜的判据。**

于是：

- **X=85% 是真参数**，进代码
- **Y=30% 是预期落点不是输入参数**，不进代码——两档的实际动作都是「把保护区之外的
  全部处理掉」，落到哪算哪（跟第八问用户主动摘要那句「压到多少算多少」同一个道理），
  由 [110](110-compaction-dogfood.md) 量出来验证

**先清后摘的顺序、触发线、保护区全部不变**，这是澄清不是推翻。

### 待校准

X=85 是初始值，Y=30 是预期落点，都等 [110](110-compaction-dogfood.md) 真机跑完回填，
并在这里注明**是量出来的还是仍是初始猜测**。
