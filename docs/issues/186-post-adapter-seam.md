# 186 文章：别在 core 里 `match provider`

**里程碑** L · **依赖** [165](165-launch-positioning-decision.md) · **模型** **opus** · **估时** 20min · **状态** 初稿完成（2026-08-13）

## 目标

讲决策 17：**把「事前问能力」改成「事后报调整」**。

这是本仓最有转载价值的单个架构洞见——它解决的是一个**所有做多 provider 抽象的人
都会撞上**的问题，而通行解法（能力位 + 分支）是错的。

## 素材

决策 14（被取代的原案）、决策 15、决策 17，以及红线 12。

## 写什么

标题方向：*Capability flags are `match provider` wearing a hat*

论证链：

1. **通行解法**：抽一个 `Capabilities { supports_tools, supports_prefix, ... }`，
   core 里 `if caps.supports_x()` 分支。看起来干净——provider 名字不出现在 core 里了
2. **为什么它是错的**：N 个能力位 = 2^N 种组合，**其中绝大多数从没跑过**。
   加一家新 provider 仍然要回来改 core（因为它的组合是新的）。
   能力位只是把 `match provider` 换了层皮，**分支还在 core 里**
3. **改法**：core 只说**意图**，adapter 做不到就报一条 `Adjustment`。
   测试组合从 2^N 掉回 1
4. **额外白拿的**：`Adjustment` 是可观测数据——降级不再是静默的，
   它在这一轮就以事件形式浮出来，而不是下个月在账单上
5. 边界：什么该进 adapter、什么该留 core（决策 15：**请求组装归 adapter，core 只供料**；
   决策 18 压缩三分是这条原则的一次精细应用——触发和实现在 core，摆盘在 adapter，
   **因为 adapter 是纯函数无权改世界**）

## 验收

- 第 2 点的论证要**站得住**——这是全文的支点，写虚了整篇就垮了。
  关键是「2^N 组合里多数没跑过」和「加一家仍要改 core」两句都要有说服力
- 有一个具体例子贯穿（建议 prefix 续写：DeepSeek 要换 `base_url`、Kimi 不用，
  这个差异很具体且好懂）
- 读者能拿走可迁移的判据，不需要用这个项目

## 实做记录（2026-08-13）

**初稿在 `scratchpad/186-draft-en.md`。**

### 标题就是论点

*Capability flags are `match provider` wearing a hat* —— 这是 issue 里就定好的方向，
写完确认它撑得住整篇：全文都在论证这一句。

### 支点是一个读者能自套的问题，不是一段论证

本 issue 的验收第一条是「第 2 点的论证要站得住，写虚了整篇就垮了」。落地时没有
写成论证，写成了**一个问题**：

> **加第四家的时候，你要不要改 core？**

用能力位就要，而且是结构性的：新那家带来一个没人产生过的位组合，走的是一条
**从没执行过的路径**。四位十六种组合，你有三家，最多跑过三种。
**能力位没有消除分支，只是把厂商名从分支里拿掉了**——于是更难看出到底在按谁分支，
而分支数其实变多了。

补了一个更早显形的症状：**你会不停地加位**。每次集成都冒出一个新差异，每一次添加
单独看都合理，而组合空间每次翻倍。**一个每接一家就长一个字段的结构体不是对厂商的
抽象，是厂商清单转置了一下。**

### 「事后报调整」为什么成立，落在一句被容易略过的话上

> **强制工具调用在任何一家都不是保证。** 就算 API 收下了你的 `tool_choice` 不报错，
> 模型也可能回别的东西。

所以 core **本来就需要**「拿到结果再判断对不对」这条路——它已经存在、已经被测、
每轮都在跑。既然如此，事前的能力检查什么都没买到：它是同一个问题的第二套、
更不可靠的答案，而且是**事前**用一份静态的 provider 描述回答的，
而不是**事后**用真回来的东西回答的。

### 边界那一节用了决策 18，因为它是最难的那个例子

「provider 相关的放 adapter」太虚，落不了地。文章给两条：

1. **请求组装归 adapter**（决策 15）
2. **但 adapter 无权改世界**——纯函数

第二条决定了真正难的分案。压缩三分逐条对着 ROADMAP 决策 18 写：
触发在 core（纯算术，**红线 12 禁分支不禁参数**）／实现在 core（状态变更，
走 command 层进 undo log）／压后摆盘在 adapter。

关键那句照搬了决策 18 的理由并展开：**adapter 偷偷压，prompt 和状态就对不上，
undo / 审计 / 前缀镜像一起断**。落成一句可记的话——
**adapter 翻译，不改写**（translate, don't mutate）。

### 诚实成本那一节没省

两条，都不免费：

- **你是事后才知道的**，而且是花了钱之后。反驳理由用了 [183](183-post-providers.md)
  的实测：**厂商文档在两个相反方向上都错**（一家文档说支持四种实际拒两种，
  一家文档说只支持一种实际四种全行）。**能力位是一句你手工维护、从不验证的
  关于 provider 的断言；Adjustment 是一次真实发生过的请求的观测。**
- **得有人看 Adjustment**。没人读的数据比分支更糟——分支好歹还干活。
  只落进日志文件的话，你造的是一套非常整洁的忽略问题的机制。

### 偏离了验收第二条，理由在这

issue 建议「有一个具体例子贯穿（建议 **prefix 续写**：DeepSeek 要换 `base_url`、
Kimi 不用）」。**没照做**，改用了 `tool_choice` × 思考模式那组。理由：

- prefix 续写的差异是**换个 URL**——它是配置差异，不需要 core 做任何判断，
  所以它证明不了「能力位分支为什么错」。用它当例子会削弱支点。
- `tool_choice` 那组才是真正的形状：DeepSeek 默认开思考、`required` 直接 400、
  显式关思考才行；Kimi 思考常开且没有关闭字段，于是**指定函数永久不可用**。
  这里 core 想要的东西（「这轮必须调 `fs/read`」）在三家有三种命运，
  **而且其中一种是做不到**——正是「事后报调整」要处理的那个情形。
- 三个 `Adjustment` 变体里有两个（`ToolChoiceDowngraded`、
  `ThinkingDisabledForToolChoice`）就是为这组存在的，例子和代码能对上。

**验收的意图是「要有具体例子贯穿」，那条满足了；建议的那个具体例子换掉了。**
