## 真机记录（主会话，2026-08-10）

### ⚠️ 跑法：用配置的小窗口，不是真的烧满 1M

前置落地后查到三家的真实窗口**都是 1M**（`providers.example.toml` 注了查证日期）。
撑到 85% 就是 **85 万 token**——那对验证机制没有任何增量，只是烧钱。

所以 dogfood 用的是**配置的小窗口**：`context_window = 20000`（第 2 档那三条）
与 `8000`（逼出第 3 档那条）。`context_window` 本来就是配置参数、代码用的就是它，
走的是**完全相同**的触发→清除→摘要→投影链路。

配置放在 scratchpad 的副本里，经 `AGENT_PROVIDERS_CONFIG` 指过去，
**没有改用户的 `providers.toml`**；跑完即删（副本带真 key）。

**模型档位**：DeepSeek 用的是 `deepseek-v4-flash`（缓存折扣 ≈50x），
不是 `v4-pro`（≈120x）。M12 文档里那些「一次压缩 ≈120 轮命中的钱」是按 pro 算的，
**对不上账时先看档位**。

### 第 2 档：三家全部正确开火

脚本：读三个大文档（`STATE-MODEL` 28218 字节 / `INVARIANTS` 11953 / `ADAPTER` 15864）
+ 三轮纯文本，共 9 跳。

| | 触发前 prompt | 压缩后 prompt | 降幅 | 恢复轮命中率 |
|---|---|---|---|---|
| DeepSeek | 22735 | 14979 | −7756 | 14976/14995 = **99.9%** |
| Kimi | 20789 | 13548 | −7241 | 13312/13592 = **97.9%** |
| GLM | 22034 | 14429 | −7605 | 14400/14444 = **99.7%** |

三家的压缩轮**全部判成「预期内，这一轮全价」**——[103](103-prefix-intent-wiring.md) 的
`PrefixIntent` 在真机上**零误报**。

**只清了 1 个工具结果，这是对的**：三次工具调用在第 1/2/3 轮，压缩发生在第 4 轮，
`protect_recent_turns = 3` 让保护区从倒数第 3 条 user 消息（第 2 轮）起算，
**够得着的只有第 1 轮那个**。而被清的正是最大的 `STATE-MODEL.md`
（28218 字节 ≈ 7.7k token），**跟实测 7756 的降幅几乎逐 token 对上**。

### 第 3 档：真的用子 agent 摘要了

第 2 档够用时第 3 档一次没开火（阶梯顺序兑现）。为验第 3 档，另跑一条
`context_window = 8000` + **纯聊天**（第 2 档无可清）：

```
[a1] --- usage: prompt=725  completion=445   ← 真的子 agent 在做摘要
[压缩] 摘要 summary@2 已生效，覆盖前 2 条消息（turn=4）
--- usage: prompt=7378 cached=6656
发前比对：History 段变了，本轮本来就打算改前缀（预期内，这一轮全价）
```

`SummaryId` 是 `summary@2` / `summary@4` / `summary@6`——[107](107-summary-writeback.md)
「从 `upto` 派生」的形状在真机上可见。摘要子 agent 的请求只有 725～1160 token，**很便宜**。

### ⚠️ 一个跟设计直觉相反的实测发现

那条 8000 窗口的会话**连着三轮都在压**（固定前缀 tools+system+skills 就有 6.6k，
占窗口 83%，压缩只能削 History 那一小块）。按 E6 的直觉这该是灾难。

**实测不是**：压缩轮的命中率是 **90%**（`prompt=7378 cached=6656`）——
Tools/System 段没动、照样命中，全价的只有很小的 History 部分。
第 3 层滚动窗口全程 92–96%，**正确地没有告警**。

**结论**：[PROVIDERS.md](../../probes/PROVIDERS.md) 那个「一次压缩 ≈120 轮命中的钱」
**隐含假设是「历史是大头」**。固定前缀占比高的时候，压缩在缓存上其实很便宜，
真实成本变成了摘要那次模型调用。**这条以后引用 E6 数字时要一起读。**

代价确实存在但换了形态：6 轮里 3 次摘要调用。这是**配置病态**（窗口只比固定前缀
大一点点），不是阶梯的 bug——但**系统不会告诉你这一点**。
`context_window` 逼近固定前缀大小时该有个提示，见「延后」。

### 完整记录 / undo / 崩溃恢复

- 压缩后的会话文件 **1.6 MB**，被清掉的那个工具结果**原文还在里面**
  —— [095](095-compaction-tiers.md) 「完整记录永不压缩」在真机兑现
- 杀掉进程重开：`[会话已恢复] 接着第 6 轮继续`
  —— [100](100-projection-into-ingredients.md) 那个 `KNOWN_LABELS` 坑的修复真机验证
- 压缩之后 `/undo`：`[已撤销] 第 6 轮，3 条`
  —— **压缩不是 undo 屏障**（095 第 5 点）真机兑现

### 水位校准结论

- **X = 85% 保持**。三家都在过线后的下一轮准确开火，没有早压也没有晚压
- **Y = 30% 不是参数**（[108](108-tier-ladder.md) 已澄清），本次不涉及。
  实测落点：第 2 档一次全清后落到 **68–75%**（`14979/20000` 等），
  比 30% 高得多——因为够得着的本来就只有一个工具结果。
  **「落到 30%」是历史很长时的预期，不是每次都该达到的目标**

### 延后（不阻塞 M12 收官）

1. **`context_window` 逼近固定前缀大小时给个提示**——现在会静默地每轮都摘要
2. **`v4-flash` vs `v4-pro` 的折扣差**没有实测覆盖，E6 的 120x 仍是 pro 档的推断
