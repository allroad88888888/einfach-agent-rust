# 024 缓存兜底三层

**里程碑** M1 · **依赖** 023 · **模型** opus · **独立测试 agent** ✅ · **状态** 完成

## 目标

前缀缓存失效时**当场知道**，而不是月底看账单才知道。

## 为什么这是 M1 而不是优化项

缓存失效**不报错、不影响任何功能**，只是每一轮都全价。最贵的那家是 120 倍。
一个「一切正常」的 bug 跑一个月，代价是四位数。

红线 11 存在的全部理由就是防这个，而红线需要一个能实检它的东西——就是本 issue。

它同时是**花费失控的事后闸**。事前闸（016 的 `max_turns`、第 1 层的发前比对）拦的
是已知模式；agent 进死循环这类没料到的模式，形态恰好是第 3 层的信号——每轮全价、
命中率崩、单位轮次花费异常。事前挡已知，事后兜未知，两边缺一不可。

## 做什么

### 先切一刀：判断归 adapter，比对归 core（红线 12）

| | 谁做 | 为什么 |
|---|---|---|
| 「这次该命中多少 token」 | adapter | 要看匹配语义（前缀树还是仅扩展）和块粒度 |
| 「哪一段漂了」 | adapter | 它才知道自己把料摆成了什么顺序 |
| 预测 vs 真实，差太多告警 | **core** | 纯算术 |
| 滚动窗口命中率低于阈值 | **core** | 纯算术 |

所以 `Ingredients` 带 `prev_prefix`，`Encoded` 回 `drift` 和 `predicted_cache`
（见 [../ADAPTER.md](../ADAPTER.md)）。**core 这边零个模型相关判断。**

三层，按「多快发现」排，不是按「多准」排：

### 第 1 层 发前比对（不花钱）

留上一次请求的前缀镜像，这次发之前比一下：**该复用的段真的逐字节没变吗？**

镜像按段打标记（`[Tools][System][History]`），对不上时能说出**是哪一段漂了**——
只报「前缀变了」等于没报，一千条消息里找不出是哪个字段的 key 顺序翻了。

这一层抓的是我们自己的 bug，**在花钱之前**。

### 第 2 层 对账（花一次钱）

发前预测「应该命中 N 个 token」，响应回来跟真实 `cached_tokens` 对。
差太多说明我们对这家的缓存语义理解错了。

已知局限：只留一个镜像，就只能判断「跟上一次相比」，判不出「跟三轮前那个分支相比」。
留最近 N 个镜像更准，等真遇到再加（ROADMAP §四）。

### 第 3 层 滚动窗口（花很多次钱才发现）

最近 N 轮的命中率，低于阈值告警。抓的是前两层都漏掉的慢性失效。

### 三家的 usage 字段不一样

一家未命中时字段值为 0，另一家**整个字段缺失**。
`Option` 的 `None` 和 `Some(0)` 在这里语义不同：前者是「这家不报」，
后者是「真的没命中」。**当成一回事，第 2 层就永远对不上账。**

## 验收

- 第 1 层：构造一个「`HashMap` 导致 key 顺序翻转」的输入，**它必须被抓到，
  且报出是哪一段**
- 第 1 层不发任何 HTTP（纯函数，单测零网络）
- 第 2 层：喂录制的 usage，命中数对得上时不告警，差 30% 以上时告警
- 第 2 层：字段缺失 vs 字段为 0，两种输入走不同分支，有各自的断言
- 第 3 层：十轮全命中不告警；连续三轮 0 命中告警
- **三层的告警各自可分辨**，不是同一个布尔
- **`agent-core` 里 grep 不到厂商名、`Capabilities`、`caps.`**（红线 12）——
  块粒度、匹配语义这些只出现在 adapter 里

## 注意

- 红线 1：判读函数必须是纯函数，不读时钟不读随机。滚动窗口的「最近 N 轮」
  按轮次计数，不按时间。
- 红线 11：本 issue 是这条红线唯一的实检手段。第 1 层的测试用例要**主动构造违反**，
  不能只测正常路径——只测正常路径的话，这一层写错了也全绿。

**为什么 opus + 独立测试 agent**：三层全写错也不会有任何测试变红、任何功能异常。
唯一的信号是账单。这是 [WORKFLOW.md](../WORKFLOW.md) 第三档最典型的一个。

## 实做记录（2026-08-01，core 侧判读）

`crates/agent-core/src/cache/`：`drift.rs`（第 1 层）/ `reconcile.rs`（第 2 层）/
`window.rs`（第 3 层）/ `report.rs`（三层共存与告警）/ `mod.rs`（时序与局限）。
adapter 侧的料（`Encoded.drift` / `predicted_cache` / usage 的 `None` vs `Some(0)`）
022 已经在真实调用里转过，这次只做纯算术比对。全部判读是自由函数，无可变状态。

判断与理由：

- **没有 `evaluate()` 一次算完三层**。第 1 层的输入在请求发出**之前**就齐了，
  合成一个入口等于把它挪到花完钱之后跑，这一层就白做了。宿主的顺序写死在模块
  文档里：`encode → check_drift →（发请求）→ reconcile + check_window → GuardReport`。
- **「有没有有意改前缀」是 `PrefixIntent` 不是 `bool`**。`check_drift(Some(Tools), false)`
  在调用处读不出 `false` 是哪一边，而传反的后果正是这一层要拦的东西：事故被
  当成预期静默放过。M1 恒 `Reuse`。
- **默认容差 0 token**。任何非零默认值都得回答「一个块多大」——那是块粒度，
  写进 core 就违了红线 12。也不需要：adapter 的预测向下取整，零头只会让实际
  比预测**多**，落进「好于预期」（信息级）；少的那一侧由 30% 的相对阈值兜着，
  跟粒度无关。容差仍是参数，宿主要压零头噪声可以传非零值。
- **30% 是「超过」才告警**，边界（缺口恰好 30%）算一致。边界两侧各有一条测试。
- **第 2 层五态**：`Blind`（这家没报，本轮不工作）/ `NoPrediction`（predicted=0，
  不判，但带出实际命中数）/ `Match` / `BetterThanExpected` / `Shortfall`。
  `predicted=0` 且 `cached=None` 时报 `Blind`——没有真实数字就谈不上对账。
  措辞按 022 的教训分开：好于预期那条里没有「告警」也没有「对不上」。
- **第 3 层默认 窗口 10 / 单轮低命中 50% / 连续 3 轮告警**。窗口太短跟「连续 K 轮」
  重合，太长则一次真实的前缀变更要拖几十轮才淡出。触发条件是**连续 K 轮**而不是
  窗口均值：均值滞后，且一次合理的全价重编码就能把它拖下去。窗口整体命中率照样
  报，但只是给人看的数字。
- **失明轮不进窗口，也不打断连续性**——它对第 3 层是不存在的。折算成 0 命中的话，
  不报 `cached` 的那家会被判成天天缓存全崩。
- **告警是 `GuardAlert` 的三个变体**，带 `layer()`；失明/无预测/无数据**不是告警**
  （混进去会让人去修一个不存在的 bug），要看失明状态就读对应那层的 verdict。

已知局限记在模块文档里：第 2 层只跟上一次比（ROADMAP §四）；第 3 层在连着几轮
小 prompt 时会误报，那几轮本来就便宜，真被烦到再加最小 prompt 门槛——那个门槛的
取值只有 adapter 说得清。

测试：`tests/cache_guard_{preflight,reconcile,window,report}.rs` 共 30 条 + 5 条
doctest。第 1 层的 key 顺序翻转用写死的两份字节构造（真 `HashMap` 在同一进程里
不保证抖，那样的测试会偶发绿），并有一条 grep 元测试盯着 `src/cache/` 里不出现
时钟/随机/网络。
