# 004 工具结果的大小上限（决策 + 实现）

**里程碑** M1 · **依赖** 无 · **模型** opus · **独立测试 agent** 决策类不派 · **状态** 完成

## 目标

定一个工具结果的大小上限并实现截断。

**不依赖 loop，第一天就能开工。** 它只需要在 013 实现工具之前定完——把它排在 003
之后是我一开始排错了，决策不需要等实现。

## 为什么是必须的

一个工具返回 10MB，会顺着 `Messages` 进下一轮 prompt。不做这件事，第一次有人写个
`grep -r` 工具就炸——而且是那种「昨天还好好的」的炸。

## 要定的

1. **上限取多少**。建议按 token 而非字节（字节数和 token 数关系不稳定），
   但我们没有 tokenizer——所以实际只能按字节估，需要定一个保守的换算比。
2. **截断后怎么标记**。必须让模型知道自己看到的是残缺的，否则它会基于不完整的数据
   下结论。建议在截断处插入明确的标记文本，而不是静默切断。
3. **谁来截断**。core 边界（它知道预算）还是 tool executor（它先拿到结果）。
   倾向 core——executor 不该知道 prompt 预算。

## 验收

- 10MB 的工具结果不会让下一轮 prompt 爆炸
- 截断标记在 prompt 里可见，且模型能据此判断要不要换个方式查
- 上限可配置，默认值写明理由

## 注意

这条和红线 5（大值必须 `Arc`）配合：截断后的结果仍然可能几十 KB，进
`AgentValue::Json(Arc<_>)` 是对的。

## 决策记录（2026-08-01 拍板）

四个点，前两个用户拍板、后两个常规判断直接定，全部进 ROADMAP 决策 19：

1. **上限默认 32 KiB**（≈8k 英文 / 7–10k 中文 token）。备选 16/64 KiB 都摆过：
   16 逼模型频繁分页多烧轮次，64 让一轮多工具时 prompt 膨胀更快。可配置，
   `truncate_tool_output` 收 `limit` 参数，默认值是 `DEFAULT_TOOL_OUTPUT_BYTES`。
2. **只留头部 + 尾部标记**。文件读取和 grep 头部信息密度最高、实现可预测；
   M2 的 `shell/exec`（错误常在尾部）到 020 再议头尾各半。
3. **core 边界截断**（`ToolResult` 进 `Messages` 之前），executor 不知道 prompt 预算。
4. **标记逐字节确定**（红线 11，它进 prompt）：只含原始大小、保留大小、
   「缩小范围重调」指引；无时间戳无随机 id。

实现与测试在 `crates/agent-core/src/limits.rs`（106 行，6 测试）：
UTF-8 边界安全（中文 3 字节字不从中间切）、10MB 输入有界、两次调用逐字节相同。
内容预算恒等于 `limit`，标记追加在外——「上限」约束的是失控的工具输出不是标记，
这样比「内容+标记 ≤ limit」好预测。
