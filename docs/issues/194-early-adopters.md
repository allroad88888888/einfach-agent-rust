# 194 找 3–5 个真实嵌入用户

**里程碑** L · **依赖** [191](191-launch-post.md) · **谁做** **用户**（我做不了） · **估时** 持续 · **状态** 材料就绪，**等首发后开始**（2026-08-13）

## 目标

让路线图**从猜测变成回应**。

CLAUDE.md 里已经写着这条原则：多租户、多副本 `RedisRegistry`、MCP 的 OAuth
「都等真实使用反馈再定，别提前猜」。这个 issue 就是去拿那个反馈。

021 那句话是同一个意思：**没被真实使用验证过的东西跟没写一样**。

## 为什么必须用户做

要找人聊。我可以准备材料，接触本身得你来。

## 做什么

1. 从首发（[191](191-launch-post.md)）的评论区和邮件里筛**真的在做嵌入**的人——
   不是「这个看起来很酷」，是「我正在给我们的后台加 agent」
2. 每个人问三件事：
   - 你的宿主是什么形态（浏览器 / 服务端 / 桌面）
   - 你的工具从哪来（自家接口 / MCP / 都有）
   - **你的第一个障碍是什么**（这一条最值钱）
3. 障碍逐条记进 issue，成为下一个里程碑的输入

## 验收

- 3–5 个真实对话记录（不是 star 数）
- 至少一条障碍**变成了 issue**
- 明确记下**没人提的东西**——如果 5 个人里没有一个人问多租户，
  那它就该继续排在后面。**这是本 issue 的隐藏价值**：它同时告诉你别做什么

## 注意

早期用户的意见容易被过度加权。**一个人提的不是需求，三个人提的才是。**
记录时把「谁提的」写清楚，别把一次对话写成「用户们希望」。

## 材料就绪（2026-08-13）

接触本身要你来（**这条我做不了，也不该代做**），但问什么、怎么记，可以先定死，
免得到时候临场发挥、三个人问出三套不可比的答案。

### 三个问题的确切措辞

本 issue 原文定了三件事要问，这里把它们变成可以照念的句子——
**开放式提问会得到一堆不可比的故事，闭合式会漏掉你没想到的答案**，所以是
「闭合选项 + 一个开放追问」：

1. **宿主形态**
   > 你打算把它嵌在哪一侧：浏览器前端 / 你们自己的服务端 / 桌面应用 / 其它？

2. **工具从哪来**
   > 你要给 agent 的工具，主要是你们自家的接口，还是已有的 MCP server，还是都有？

3. **第一个障碍**（最值钱的一条）
   > 你从看到这个项目到「决定不用它」或者「卡住了」，中间**最先撞上的是哪一步**？

第 3 条特意问「最先撞上的」而不是「你觉得缺什么」：
**前者是他真的经历过的事，后者是他的想象**。想象出来的需求列表是最容易把路线图
带偏的东西。

### 记录格式（每人一段，进本 issue）

```
日期 / 来源（HN 评论 / 邮件 / issue #N）
形态：
工具来源：
第一个障碍：
原话（一两句，别转述成需求）：
```

**「原话」那栏是硬要求**：转述会不自觉地把对方的话翻译成自己已经想做的事。
留原话，半年后回看才知道当时到底听到了什么。

### 判据（本 issue 原文那条，展开）

> **一个人提的不是需求，三个人提的才是。**

具体操作：每条障碍标上**谁提的**。同一条被三个不同来源提到，才进路线图；
一次两次的先躺在这里。

**并且要显式记「没人提的东西」**——这条是本 issue 的隐藏价值。
CLAUDE.md 里明确未排期的三样（多租户、多副本 `RedisRegistry`、MCP 的
OAuth/resources/prompts）如果五个人里没有一个人问，那它们就该继续排在后面，
而这个「没人问」本身要写下来，否则下次又会有人凭直觉觉得该做了。

### 别做的事

- **别在对话里承诺排期。** 记下来就够了；当场答应会把「一个人提的」变成事实上的需求。
- **别把这条当获客。** 它的产出是路线图输入，不是用户数。混起来会让你倾向于
  听那些「听起来快要用了」的人，而他们恰恰最不会告诉你真实障碍。
