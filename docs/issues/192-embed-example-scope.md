# 192 嵌入样例：定场景与验收（决策）

**里程碑** L · **依赖** [191](191-launch-post.md) · **模型** **opus** · **独测** 决策类 · **估时** 20min · **状态** 完成（2026-08-13）

## 目标

**宿主声明能力是这个项目最独特的东西**（M10 / M14 / M17 三个里程碑都在做它），
但现在没有任何一个例子能让人**直观看到它值多少钱**。

`examples/java-gateway/` 今天是「参考实现」——证明能接通，不证明有用。
这个 issue 先定清楚要做一个什么样的例子，别上来就写代码。

## 要定的三件事

### 1. 场景选哪个

判据：那个场景里，**「宿主声明工具」必须比「把工具写死在 agent 里」明显更好**。
否则读者会想「那我直接写死不就行了」——那样这个例子就是负分。

候选方向（选一个，别贪多）：

- **后台管理系统**：agent 能调这个后台已有的业务接口，且**不同租户的接口不一样**
  → 写死不可能，声明是唯一解
- **表格/财务工具**：agent 操作当前打开的那份文档 → 工具的执行体在浏览器里，
  Rust 侧结构上够不着
- **权限差异**：同一个 agent，不同角色的用户能用的工具不同 → 会话级声明 + journal 的价值

### 2. 用哪个宿主形态

Java 网关（企业味最正，但读者要装 JDK）vs 浏览器 wasm（零门槛，且能直接挂 demo）。
**倾向浏览器**——它能复用 [170](170-pages-workflow.md) 的部署路径，且第二个 demo 的边际成本低。
但企业读者是这个项目的真实目标用户，Java 那条更贴。**这是本决策的主要取舍。**

### 3. 验收标准

例子做到什么程度算成？建议：**一个读者能在 5 分钟内看懂「为什么这里非要声明不可」**。

## 验收

- 三件事各有结论和理由
- 产出一份可执行的任务清单给 [193](193-embed-example-build.md)，
  **并对 193 是否超过 20 分钟给出诚实估计**（大概率超，那就在这里继续拆）

## 注意

这个 issue 排在 [191](191-launch-post.md) 之后不是因为不重要，而是因为
**首发后的真实反馈会改变场景选择**。先发，看别人问什么，再决定做哪个例子。

## 拍板（2026-08-13）

### 一、场景：**同一个 agent，不同角色能用的工具不同**

判据是本 issue 自己写的：**那个场景里「宿主声明工具」必须比「把工具写死在 agent 里」
明显更好**，否则读者会想「那我直接写死不就行了」。

三个候选按这条判：

| 候选 | 判 |
|---|---|
| 后台管理系统调自家接口 | ❌ 读者会想「写死一份也行啊」——除非强调多租户接口不同，但那要先解释租户模型，绕 |
| 操作当前打开的文档 | ⚠️ 「执行体在浏览器里、Rust 够不着」很有说服力，但它证明的是**位置透明**，不是**声明** |
| **不同角色 → 不同工具** | ✅ **写死在结构上不可能**：同一个部署、同一个 agent，工具集随调用者变 |

选第三个，再加一个第二候选给不了的东西：**它天然演示 journaled 与恢复**。
一个 viewer 角色的会话在恢复之后**仍然是 viewer**，即使宿主今天的角色表变了——
这正是 073「恢复是忠实重放，不是用今天的配置重建」的用户可见形态。

具体形状（一个假的运维台）：

```
role=viewer    web:orders/search             只读
role=operator  web:orders/search + refund    refund 声明为 irreversible
```

于是四件事在**一个例子**里同时可见：
声明（两个角色两份工具表）／位置透明（工具在宿主执行）／可逆性屏障
（refund 之后 undo 被拦住并说出是谁拦的）／恢复（viewer 会话恢复后仍是 viewer）。

### 二、宿主形态：**浏览器 wasm**

Java 网关企业味更正，但读者要装 JDK + Maven 才能跑，**漏斗在第一步就断**。

浏览器那条能复用 [170](170-pages-workflow.md) 的部署路径，第二个 demo 的边际成本
接近零——而且**读者点开就能自己切角色**，不是看截图。

> Java 那条不是不做，是**等有人问**。[194](194-early-adopters.md) 要是有两个以上的人
> 问「怎么在 Spring 里嵌」，那时候再做，而且那时会知道他们真正卡在哪一步。
> 现在做等于替一个不存在的用户猜。

### 三、验收标准：**5 分钟内看懂「为什么这里非要声明不可」**

具体化成一句可判定的：**读者能说出「把工具写死在 Rust 里，这个例子做不出来」的理由。**

说不出就是例子失败了，不管它跑得多顺。

## 交给 [193](193-embed-example-build.md) 的清单

1. 新页面（`crates/agent-wasm/www/roles.html` 或独立目录），顶部一个角色切换
2. 两份 `capabilities.tools` 声明，按角色选一份传给 `AgentHost`
3. `web:orders/search` / `web:orders/refund` 的执行体在页面里（假数据，几十行）
4. `refund` 声明 `reversibility: "irreversible"`
5. 会话 id 带角色（`demo-viewer` / `demo-operator`），演示恢复
6. 页面文案点破那句话：**同一个部署、同一个 agent，工具集随调用者变——
   写死在 Rust 里做不到这件事**

## 对 [193](193-embed-example-build.md) 工时的诚实估计

**超过 20 分钟，估 60–90 分钟**（本 issue 验收要求给这个估计）。构成：
页面骨架与角色切换 ~20min、两个假工具的执行体 ~15min、
可逆性屏障与恢复的真机验收 ~20min、文案与 README 挂链 ~15min。

按仓库规矩要拆。建议拆成三条：

- **193a** 双角色声明 + 两个假工具跑通一轮（20min）
- **193b** refund 的不可逆屏障 + 恢复后角色不变，两条真机验收（20min）
- **193c** 页面文案 + README/demo 入口挂链（20min）

**但先别拆。** 本 issue 排在 [191](191-launch-post.md) 之后是有理由的——
**首发后的真实反馈会改变场景选择**。要是评论区没有一个人问「怎么嵌进我的产品」，
那这个例子服务的就是一个不存在的用户，[021](021-skeleton.md) 那条判据在这里同样成立。

先发，看别人问什么，再决定做不做、做哪个。
