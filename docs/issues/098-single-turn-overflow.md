# 098 单轮超窗兜底（决策）

**里程碑** M12 · **依赖** 无 · **模型** opus · **独立测试 agent** 决策类不派 · **状态** 完成（2026-08-10 拍板）

## 目标

定「这一轮本身就装不下」时的行为。

跟压缩阶梯无依赖——阶梯解决的是「历史太长」，这条解决的是「当前这一轮太大」，
五档里没有一档救得了它。可与 095/096 并行拍板。

## 为什么必须定

[096](096-compaction-trigger.md) 第一问的决定是「触发只看上一轮实测 token，接受滞后
一轮」，代价明写了由这条接住。不定它，滞后那一轮爆掉的时候行为是未定义的。

真实触发场景三个：用户粘贴一个巨大文件、一个工具返回本身几十 KB、
一轮里模型并发调了十个工具。

## 要定的

1. **第 1 档的 32 KiB 够不够**。[004](004-tool-result-limit.md) 定的
   `DEFAULT_TOOL_OUTPUT_BYTES` 管的是单个工具结果。一轮十个工具就是 320 KiB，
   单条不超但一轮超。要不要加一个**轮级**上限？
2. **`Adjustment` 能否配成硬失败**。ROADMAP §四第三条记着这个未决问题，
   原话是「『必须调 `fs/read`』被降级后继续跑，某些场景比直接报错更糟」。
   M1 至今只打印。现在有了具体场景，可以定了。
3. **谁来判、判完做什么**。倾向 core 边界（跟 004 第 3 点一致，executor 不知道
   prompt 预算）。判完是截断 + 报 `Adjustment`，还是直接拒绝这一轮？
4. **用户消息本身就超窗怎么办**。用户粘 500 KB，截断它跟截断工具输出不是一回事
   ——用户会认为自己粘过去了。至少要让他知道。

## 验收

可判定的四条（按下面的决策记录）：

- **用户输入 10 001 个字符：被拒绝**，错误里带上实际字符数与上限，
  内容**不进历史**——不是截断后照收
- 用户输入 10 000 个字符：正常收下
- 一个 60 KiB 的**工具**返回：走既有的 32 KiB 单条截断 + 截断标记，
  **不因为「一轮总量」被额外拦一次**
- 一轮并发十个工具、每个 32 KiB：每条各自截断，**不报轮级超限**——
  「工具获取的不限制」的字面意思

## 注意

- **红线 11**——任何截断标记都进 prompt，逐字节确定，无时间戳无随机 id（照 004 的做法）
- **红线 12**——「窗口多大」是参数不是分支；判断只做算术
- 跟 004 是同一族问题，拍板后建议在 004 的决策记录里加一行交叉引用，
  免得以后有人只读 004 就以为上限这事定完了

## 决策记录（2026-08-10 拍板）

**用户直接拍板第 1、4 点**，第 2、3 点按倾向定。

### 1 + 4. 用户输入限死 10 000 字符；工具获取的不加轮级上限 —— 用户拍板

两个来源分开管，这是本 issue 的核心裁决：

| 来源 | 上限 | 超了怎么办 |
|---|---|---|
| **用户输入**（打字 / 粘贴 / 拖文件） | **10 000 字符，硬上限** | **拒绝**，告诉用户实际多少、上限多少 |
| **工具返回** | 沿用 [004](004-tool-result-limit.md) 的**单条 32 KiB**截断 | 截断 + 标记，照旧 |

**不加「一轮总量」上限**——原倾向建议加一个（十个工具各 32 KiB = 320 KiB），
用户明确否掉：agent 自己取的东西不限制。理由站得住：轮级上限会让 agent 在
「这轮已经读了三个文件」时读第四个失败，而它没法预知也没法规划，
表现成随机的工具失败；单条 32 KiB 已经挡住了「一个 `grep -r` 返回 10 MB」
那类真实爆炸，剩下的交给压缩阶梯（[096](096-compaction-trigger.md)）按窗口压力处理。

**「不限制」不等于取消 004 的 32 KiB**——那条保留。取消它等于推翻一个已上线的
决策，10 MB 搜索结果会直接进 prompt。

单位是**字符**（`chars().count()`）不是字节：中文 10 000 字 ≈ 30 KB UTF-8，
英文 ≈ 10 KB。按字节算会让中文用户能贴的内容只有英文用户的三分之一。

**拒绝而不是截断**，因为用户输入被悄悄截断是最坏的一种失败——他以为贴进去了，
模型没看见，回答还挺像样，他永远发现不了（同 [IMAGES.md](../IMAGES.md) §四
「静默丢图」那条）。拒绝他能当场看见并自己拆分。

前端应该在输入框显示字数，**让人根本走不到拒绝那一步**；服务端那条是兜底，
不是唯一防线。

### 2. `Adjustment` 可配置成硬失败，默认继续跑 —— 按倾向定

ROADMAP §四挂了很久的未决问题，随本 issue 结掉。默认行为不变（打印 + 继续），
新增一个开关让宿主选择把某类 `Adjustment` 升级成硬失败。

理由：「必须调 `fs/read`」被降级后继续跑，某些场景确实比直接报错更糟；
但把它设成默认会让现在跑得好好的会话开始炸。**可配 + 默认不变**是唯一
不赌的选择。

### 3. core 边界判，判完截断 + 报 `Adjustment` —— 按倾向定

跟 004 第 3 点一致：executor 不知道 prompt 预算，判断归 core 边界。

### 注意

用户输入那条上限的**错误文案会进用户眼睛，不进 prompt**，所以不受红线 11 约束；
但工具截断标记进 prompt，仍然逐字节确定（004 已经定死，别在这里另开一套）。
