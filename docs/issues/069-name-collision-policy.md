## 为什么现在提

然后全文再没有出现过任何冲突策略——**它从没被定下来过**。这次改文档时把那句改成了
如实描述现状，并把决策留到这里。

同时发现一处**悬空引用**（本 issue 只记账，不动代码）：
`crates/agent-runtime/src/skill/mod.rs` 的 `SkillRegistry::load` 文档注释写着

> **合并**：后一个目录里同名 skill 覆盖前一个（跟工具表「后来居上」一套规则，TOOLS.md §多来源）。

括号里两件事都不成立：TOOLS.md 没有 §多来源 这一节，也从没写过「后来居上」；
而工具表**根本不是**后来居上（见下表第一行，它压根不检测重名）。

## 现状：三条路各行其是

| 路径 | 撞名时 | 出处 |
|---|---|---|
| **内置工具表** | **静默重复**——`ToolTable::with_*` 一路 `push`，不检测不去重；两条同名 spec 都会进 prompt 喂给模型，`declares()` 只是成员判断（`.any()`），不做消歧 | `crates/agent-runtime/src/tool_table.rs` |
| **skill 目录装载** | **后来居上**——后一个目录里同名 skill 覆盖前一个 | `crates/agent-runtime/src/skill/mod.rs` |
| **M10 宿主声明**（061 已落地） | **一律拒绝**——整份 `capabilities` 400，会话不创建；顶层 tools 与每个 skill 自带的 tools 放在**同一个集合**里判唯一性 | `crates/agent-server/src/http/capabilities/validate.rs` |
| **MCP 多 server** | 重复 server id 是**硬错误**（`ConfigError::DuplicateServerId`，不静默取后者）；工具名自带 server id（`mcp:<server>/<tool>`），跨 server 的同名工具不会撞 | `crates/agent-mcp/src/config.rs` |

**撞名时的行为完全取决于走哪条路，没人能从文档推出来。** 而且第一条最坏：静默重复不报错、
不告警，只是模型看到两个同名工具，调到哪一个取决于 provider 怎么处理重复声明——那是
本仓最怕的那类静默错值，只不过发生在 prompt 里而不是 store 里。

## 唯一有论证的那条

四者里只有「一律拒绝」写下了理由（`capabilities/validate.rs` 模块文档）：

> 悄悄把 `web:a b` 洗成 `web:a_b`，两个本来不同的声明就撞成了同一个工具名——后一个静默
> 盖掉前一个，模型调到哪一个取决于数组顺序。**静默串工具比拒绝更坏。** 同一条理由也是
> 「重名不做后来居上」的理由：**宿主自己都没想清楚要哪个，server 替它选一个只会把问题
> 推到运行时。**

这条论证对 skill 目录装载同样成立吗？值得单独想：目录装载有一个 `capabilities` 没有的
前提——**目录顺序是部署者显式给的**（内置 → 项目 → 用户），「后面的盖前面的」正是
覆盖机制本身的用途（用户想改写内置 skill 的写法）。也就是说这里的「后来居上」可能不是
偷懒，而是一个真实需求；如果是，它该被写成一条**有意的例外**，而不是继续跟工具表一起
被含糊成「一套规则」。

## 拍板

**不统一成一条行为，统一成一条红线加一条判据。** 四条路的行为继续不同——但不同的
**依据**从今天起是写下来的，不是各长各的。

### 红线（唯一一条，四条路都得满足）

> **一个名字在进 prompt 的那张表里只能出现一次，且它的描述/schema 必须就是 dispatch
> 真会执行的那一份。**

这不是风格问题。`declares()` / `snapshot()` / 五条截获闸（spawn/collect/status/skill/MCP）
与远端第五路**全部按名字查**——**一个名字只有一条执行路径**。两条同名 spec 一起进
prompt，不是「让模型来选」，是**给模型看两份说明书而只有一份对得上真正会跑的那件事**：
模型按哪一份的 schema 出参完全看它自己，以及 provider 怎么处理重复的 function 声明
（三家都没探过，`probes/results/` 里没有这一格）。**这正是本仓最怕的那类静默错值，
只不过发生在 prompt 里而不是 store 里。**

按这条红线复查，今天**只有工具表这一条路是违的**：skill 目录装载用 `BTreeMap::insert`
（合并完每 id 恰好一份）、`capabilities` 直接 400、MCP 靠名字自带 server id——三条都在
进 prompt **之前**就把撞名解决掉了。工具表是唯一把撞名**留到 prompt 里**的那条。

### 判据（决定每条路怎么满足红线）

> **撞名一律在「最早能报给有权修它的人」的那个点上失败；那个点不存在时，才退到
> 「后来的整条不进表」，绝不退到「两条都进表」。**

061 那句唯一有论证的话（「宿主自己都没想清楚要哪个，server 替它选一个只会把问题推到
运行时」）是这条判据在**有人可告知**时的特例。四条路行为不同，是因为「谁写的、还能
不能被告知、告知的代价是什么」不同：

| 路径 | 撞名的作者 | 最早可报点 | 定下来的行为 |
|---|---|---|---|
| **M10 宿主声明**（`capabilities`） | 客户端，在一次**活的请求**里 | **就是那次请求** | **整份 400**，会话不创建（061 已落地，不改） |
| **MCP 多 server** | 第三方 server | 配置解析 / 握手 | 重复 server id 是**硬错误**；工具名自带 server id，跨 server **结构上撞不了**（不改，见下「范本」） |
| **skill 目录装载** | 部署者，而且**目录顺序是他显式排的** | 没有——先后本身就是他给的信息 | **后来居上**（有意的例外，理由见下；行为不改，改注释） |
| **内置工具表装配** | 一半是程序员（五档 + CLI 链），一半是运行时数据（MCP 回包、客户端请求体） | 程序员那半 = **CI** | **`debug_assert!` + 看门狗测试**；运行时那半 = **后来的整条不进表，不 panic** |

### 逐条理由与被否方案

**A. `capabilities` 一律拒绝 —— 不改。**
两个候选出自**同一份声明、同一个作者、同一口气**，没有先后可言；替它选一个就是替它
做决定，而它此刻还站在那儿等 200/400。**被否**：「后来居上」——数组顺序是客户端序列化
出来的，同一份声明两次连接可能不同序（062 §六 第 2 条正是为这个才在进表前重排），
拿一个不稳定的顺序当仲裁依据等于掷骰子。

**B. skill 目录「后来居上」—— 不改，但升级成一条有理由的例外。**
目录顺序是部署者**显式给的**（内置 → 项目 → 用户），「后面盖前面」正是覆盖机制本身
的用途——用户想改写内置 skill 的写法，那是产品需求不是事故。它也**不违反红线**：
`BTreeMap::insert` 是**整体替换**不是字段级 merge（没有「一半 A 一半 B」的混血），
合并完每个 id 恰好一份，撞名在进 prompt 之前就确定性地没了。
**被否**：跟 `capabilities` 对齐成「一律拒绝」——一个用户往 `~/.../skills/` 里放了个
跟内置同名的目录，进程就起不来；那是把**一次本该生效的覆盖**变成一次启动失败，
方向反了。

**C. MCP 两条 —— 不改，而且它是范本。**
它在**名字层面**消歧（`mcp:<server>/<tool>`），比任何冲突策略都早一步：撞名压根不会
发生，于是不需要仲裁。**统一的方向就是这个**——能靠命名让撞名不可能发生的，就不要去
写策略。宿主注入那一路已经在吃这个红利：061 强制 `web:`/`desk:` 前缀，而内置五档
**一个都不用这两个前缀**（新看门狗测试第二条钉住了这一点），所以注入的名字**结构上
撞不上内置的名字**——这才是「061 只在一份声明内部判唯一」够用的真正依据，不是运气。

**D. 内置工具表 —— 加查重，但既不 panic 也不去重成「留两份」。**
今天它是四条路里唯一**既没有策略也没有论证**的：`with_*` 一路 `push`，
`declares()` 用 `.any()`，两条同名 spec 都进 prompt。而且**表内部今天就是不自洽的**：
`with_mcp` / `with_host_tools` 往 `BTreeMap` 里 `insert` 可逆性是**后来居上**，往 `Vec`
里 `push` spec 是**两份都留**——同一次撞名，prompt 看到两份、可逆性只认最后一份。

定下来的行为：**后来的那一条整条不进表**（spec 不 `push`，可逆性也不 `insert`）
+ **`debug_assert!`** + **一条会红的看门狗测试**。

- *为什么丢「后来的」不是「先来的」*：红线 11。工具表在 prompt 最前面，既有顺序是契约
  （每个 `with_*` 的文档都写着「只加不改」）。丢后来的 → 前面的字节一个不动；丢先来的
  → 整段前缀位移，所有会话的缓存一起作废。
- *为什么「整条」不进表，而不是「spec 丢掉、可逆性取更保守的那个」*：后者会造出一个
  **表里没有对应 spec 的映射项**，正是 `tool_table_host.rs` §「查表的门为什么按表而不按
  前缀」反对的那类隐式耦合（「这张表里有谁，谁就按声明办」）。撞名到了这一层已经是
  上游该拒没拒的漏网，这一层的职责是**保证表自洽**，不是替上游做二次仲裁。
- *为什么这不算「静默串工具」*（061 那句话的边界）：串工具 = 模型以为在调 A、实际跑 B。
  丢掉后来的**不会串**——一个名字本来就只有一条执行路径，跑的永远是那一条。丢掉的只是
  一份对不上的说明书。留着两份才是让模型按错的 schema 出参。
- **被否①：生产也硬失败（panic / 建表返回 `Err`）。** `with_mcp` 收的是**第三方 server
  的 `tools/list` 回包**，`with_host_tools` 收的是**客户端请求体**——让一个写错的 MCP
  server 或一份写错的前端声明把宿主进程打死，是把可用性交给外部。而这两条路各自已经
  有更早、更该报错的裁判点（MCP 的 `DuplicateServerId` / 握手、061 的 400）。
- **被否②：只加 `debug_assert!`，生产保持现状（留两份）。** 那等于承认「生产环境可以
  破红线」。而且唯一今天就够得着的撞名源（MCP，见下「活 bug 排查」）恰恰只在生产里出现，
  `debug_assert!` 在那儿是关着的。
- *`debug_assert!` 的份额*：五档 + CLI 链的撞名是**程序员错误**，它的正确裁判点是 CI，
  不是生产运行时——所以是 `debug_assert!` + 测试，不是运行时告警。

### 第 2 问：跨路径撞名（宿主注入的 `web:foo` × skill `late_tools` 里的 `web:foo`）

**结论：在 `ToolTable::skill_injection` 那一刻，把「工具表里已经有的名字」从
`late_tools` 里滤掉——表赢。不报错、不失败、不在这里拒。**

1. **赢家不是我们选的，是 dispatch 早就定死的。** `declares()` 为真是因为**表**里有它，
   远端第五路于是把调用派给**宿主注册的那一份**；skill 带的那份 spec 从来没有过自己的
   执行路径。滤掉它**执行侧一个字节都不变**，变的只是「不再给模型看一份它影响不了的
   schema」。这是四个子问题里唯一一个**不需要权衡**的：现状严格劣于结论。
2. **这里绝不能报错。** `skill_injection` **每轮都跑**（`provider_call::start` 组料时），
   而作者早就不在场了。轮中失败 = 会话在最坏的时刻死，且没有任何人能修它——正好是判据
   里「最早可报点」的反面。
3. **也不能指望上游全拒。** `capabilities` 的校验只看**一份声明**；064 第 3 条若让 server
   同时从磁盘 `./skills/` 装载，两条路的作者根本不是同一个人，没有共同的声明面。
4. **滤完仍然满足红线 11**：`active` 已排序，滤的判据是「表里有没有」——跟轮次无关、
   幂等，同一份激活集渲染出的字节仍逐字节相同。

**顺带定死 064 第 3 条**：**server 形态推荐不从磁盘 `./skills/` 装载**（宿主已经有声明
入口，两个来源合流只会造出「同一份请求在不同部署上行为不同」的面）。若 064 仍要开，
则**宿主声明的 skill id 撞上磁盘已装载的 id → 400，跟 061 同一条闸**——那一刻客户端还
在线，符合判据；静默让磁盘那份盖掉宿主声明的那份是本条最坏的结局。

> **064 采纳了「不装载」**（2026-08-04），而且 073 之后这条比写下来时更硬：宿主声明现在
> 是**会话状态**（journaled，恢复时逐字节复刻），磁盘上那份不是——开了合流，部署者改一下
> `./skills/` 就能悄悄改写一段**历史对话**该长什么样，正好是 073 刚堵上的那个洞。落地形状
> 是 `SkillRegistry::from_host_skills`（**构造器**，不是能接在 `load` 后面的 builder），
> 把这条决定钉进类型：想合流的人必须显式加一条合并路径，那时才轮得到上面那条 400。

**这一问的答案要抄进 062 与 064 的验收**（069 §验收 第 4 条）。

**另记一笔（不是本 issue 的范围）**：`late_tools` **完全不进 `declares()`**，所以
skill 自带的 `web:`/`desk:` 工具**今天根本执行不了**（远端第五路的 `declares` 闸挡住，
落 `unknown_tool`）——这是**可执行性**的洞，不是撞名的洞，064 第 4 条已经点名「如实处理、
别放大」。上面的过滤规则跟它不冲突：过滤只针对「表里已经有」的那些，而那些恰恰是**能**
执行的。

### 第 3 问：`skill/mod.rs` 的悬空引用
