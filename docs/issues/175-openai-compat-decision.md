# 175 OpenAI 兼容层落在哪（决策）

**里程碑** L · **依赖** [174](174-openai-compat-probe.md) · **模型** **opus** · **独测** 决策类 · **估时** 20min · **状态** 待开始

## 目标

定一件事：**「OpenAI 兼容」是第四家 provider，还是一个参数化的既有家？**

这个决策贵，因为它直接顶在**红线 12**（core 里不许有任何模型相关的判断）和
**决策 17**（事前问能力 → 事后报调整）上。选错了，加第五家的时候要改 core——
而那正是决策 17 当初要根治的病。

## 要定的三件事

### 1. 新 adapter vs 参数化既有家

三家今天都是 OpenAI 形状。那么「兼容」到底是：

- **A 案**：新增 `openai` adapter，与 deepseek/kimi/glm 并列
- **B 案**：既有三家其实是「OpenAI 形状 + 各自的特殊处」，抽出共享基座，
  `openai` 是那个**没有特殊处**的退化情形

B 案更诱人但更危险：抽共享基座意味着动三家已经真机验过的代码。
**判据建议**：看 [174](174-openai-compat-probe.md) 测出的差异量——差异小到什么程度才值得动存量。

### 2. 能力位怎么填

决策 17 说 core 不问能力、adapter 做不到就报 `Adjustment`。但「OpenAI 兼容」
是一个**开放集合**：同一个 adapter 后面可能是 OpenAI、也可能是 Ollama 跑的小模型，
两者的能力天差地别（prefix 续写、工具调用、缓存字段全都不一定有）。

**这是本决策最难的一点。** 配置里让用户声明？还是一律按最小公倍数、
做不到就报 `Adjustment`？后者更符合决策 17 的精神——**倾向后者，但要在这里写下理由**。

### 3. `beta_base_url` 一类的东西怎么办

DeepSeek 有 `beta_base_url`（prefix 续写要换）。通用兼容层没有这个概念。
是留空、还是让配置可选给？
