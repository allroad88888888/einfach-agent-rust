# 怎么做一个 issue

粒度、用什么模型、测试谁来写。三件事是一套：粒度决定能不能用便宜模型，
模型决定要不要单独派人写测试。

## 一、粒度：一个 issue = 一次能跑完的循环

```
读 issue → 写代码 → cargo test 绿 → check-invariants 过 → 收工
```

**一次跑不完就拆。** 判据不是「工作量大小」，是**中间有没有一个必须停下来看结果再
决定下一步的点**。有，就是两个 issue。

拆的时候按**可验证的中间态**切，不按代码结构切：

- ✅ 「移植过来能编译」→「上游测试移植通过」——两个都能独立验证
- ❌ 「写数据结构」→「写方法」——第一个验证不了什么

这四个原本偏大，已按此拆开：`007`（移植 + 验证行为 → 007/015）、
`009`（history 五件事 → 009/017/018/019）、`002`（状态机 + 停止条件 → 002/016）、
`022`（接缝定型 + 真打通 → 025/022）——最后这个还有第二个理由：接缝形状是 opus 级
判断，写 transport 和 REPL 是 sonnet 级接线，混在一个 issue 里就是拿 opus 的钱写 REPL。

拆完有个副产品：`018`（cap）从 opus 掉到了 sonnet ——**因为 cap 越界会报错，
不是静默错值**。粒度变细，判据的分辨率跟着变高，省下的是真金白银。

## 二、模型：按「错了能不能立刻发现」分，不按难度分

难度是主观的，反馈回路的长短是客观的。

| 错了以后 | 用什么 | 为什么 |
|---|---|---|
| 编译不过 / 测试红 | **haiku** | 反馈回路以秒计，错了当场知道，重试比挑模型便宜 |
| 测试绿但行为不对 | **sonnet** | 要靠人 review 才发现，反馈以小时计 |
| **不报错，只在 undo / 崩溃恢复 / 账单上浮出来** | **opus** + 人 review | 反馈以周或月计，发现时已经是数据事故或一笔冤枉钱 |

第三档不需要凭感觉判断——**[INVARIANTS.md](INVARIANTS.md) 已经列全了**：
红线 1–6、11、12 的共同点就是「违反后不报错」。

> **判据分两步。** 「注意」提到红线 1–6、11 或 12 → **必派独立测试 agent**。
> 模型档再看一步：**独测能不能把静默失败变成会红的断言？**
> 能（013 的逐字节序列化测试、023 的 encode 确定性测试）→ sonnet 就够，测试会替你红；
> 不能（024 的三层设计本身、025 的接缝归属——测试和实现出自同一份理解）→ opus。
>
> 之前这条写成「提到红线就 opus」，和表里 013、023 的评级自相矛盾——少了第二步。

不是所有看起来机械的活都能用 haiku。`008`「按职责拆五个文件」代码搬运是机械的，
但**「按什么职责拆」是判断**——拆错了不会红，只会让人半年后读不懂。那是 sonnet。

反过来 `007` 的「把上游代码搬过来让它编译」是真机械：搬错了编译器当场骂你。haiku。

## 三、测试由独立的子 agent 写

### 为什么

写实现的人写测试，测的是**自己的实现**——只覆盖想到的路径，想漏的地方测试也漏。
只读规格的人写测试，测的是**规格**。

这不是不信任，是信息位置的问题：实现者脑子里装着「我是这么做的」，那个先验会污染
测试设计。

### 什么时候必须

**碰红线 1–6、11 或 12 的 issue 必须派独立 agent 写测试**，和用 opus 是同一条判据——
因为那些红线违反后不报错，实现者的自测最容易在同一个盲点上再瞎一次。

不碰红线的可以自测，省一半 token。

### 怎么避免写出编译不过的测试

测试 agent **看不到实现体**，只看：

1. issue 的**验收**一节
2. 公开 API 的类型签名（`cargo doc` 或直接给 `pub` 定义）
3. 相关的红线条目

所以顺序是：**先定接口 → 实现与测试并行 → 合并**。这也是 `001` 必须第一个做的原因：
它把 loop 的契约定死，后面所有 issue 的测试 agent 才有东西可读。

接口没定就派测试 agent，写出来的一定编不过。

### 这套办法的前提

**验收标准的质量决定它有没有用。** 测试 agent 只有验收标准可读，验收写成
「功能正常」它就只能瞎写。

所以每个 issue 的验收必须是**可判定的断言**，不是形容词：

- ✅「3 个工具 1 个失败：loop 继续，错误作为 `tool_result` 进了下一轮的 prompt」
- ❌「正确处理部分失败」

写 issue 的时候多花的那点力气，在这里连本带利拿回来。

## 四、执行一个 issue

-1. **收工验证必须前台跑完再交报告**——不许「起后台测试 + 等通知」再收尾：
   M3/M4 期间五个 agent 栽在同一个自旋循环里（起后台跑 → 等监视器 → 醒来再起
   一轮），活干完了卷交不出来，全靠主会话按现场代收。验证就是收工的一部分，
   跑不完就是没干完。
-2. **花真钱的探针 issue 绝不并发派两个 agent**——038 期间不慎同时跑了两个消息级
   注入探针,重复烧了一点钱(数据反而双验证了,是意外之得,但别指望)。派探针前
   先确认没有同名在飞。
0. **先看仓库当前是什么样**——`ls crates/`、`git log --oneline -5`、跑一次
   `cargo test`。别信任何文档（包括这份）对「已完成」的描述。
1. **读** issue + 它「注意」里点到的红线条目
2. **定接口**（如果这个 issue 引入新的公开 API）——先写签名和文档注释，不写实现体
3. **分头**：
   - 实现：按第二节选的模型
   - 测试：碰红线就派独立 agent，只给它验收标准 + 接口签名 + 红线条目
4. **合并**，跑 `cargo test` 与 `scripts/check-invariants.sh --all`；
   **动过任何进协议面的 Rust 类型**（`SessionEvent`/`Command`/请求响应体，哪怕只改文档注释）
   → 还要跑 `cargo test -p agent-server --features ts`，红了就
   `cargo run -p agent-server --features ts --example gen_protocol_ts` 重新生成
5. **红线检查报了行数**（>300）→ 拆分是本次改动的一部分，不留「下次再拆」
6. **回填 issue**：状态改「完成」，把实际遇到的坑写进「注意」

第 6 步别省。下一个人（或下一个会话）读的是 issue 文件，不是提交记录。

**第 4 步那半句 `--features ts` 也是补上去的，代价是两处漂移。** 一致性测试
（`ts_protocol::consistency`）本身没毛病——它把整棵 `packages/protocol/src/generated/`
递归逐字节比一遍，漏不掉任何一个文件。问题在于它**只在这个 feature 下编译**，而这一步
以前只写「跑 `cargo test`」，于是每个 agent 收工都合规、也都没跑到它。等到 062 因为改了
一句文档注释才第一次跑，才发现 `Command.ts` 缺 `RemoteToolResult`、`SessionEvent.ts` 缺两个
import——**M8/M9 就漂在那儿，没人知道**。CI 里有这条，但 CI 不是每个 agent 收工时会经过的地方；
**收工清单才是**。护栏存在 ≠ 护栏在路上。

**第 0 步是补上去的，代价是三个 crate。** 之前有一轮直接照着记忆动手，
把自己上一轮抢跑写的代码当成了别人的既有实现，在错的地基上又加了一层。
文档说「已完成」是**当时**的话，`ls` 说的才是现在的话。

同样的道理反过来也成立：**issue 里没有的东西不要顺手写。** 那三个 crate 全是
计划外抢跑的产物——没有 issue、没有独立测试 agent、验收标准事后补，
最后整个删掉重来。写得快不等于走得快。

## 五、决策类 issue 不一样

`004`（工具结果上限）、`006`（子 agent 谁 spawn）这类没有代码产出，产出是**决策 +
理由**，写进 [ROADMAP.md](ROADMAP.md) 第一节。

- **一律 opus**，且必须有人拍板——模型可以摆清楚取舍，但选哪个是产品判断
- **不派测试 agent**：还没有可测的东西
- 动手写代码之前必须先定，因为它们改变后续代码的形状
