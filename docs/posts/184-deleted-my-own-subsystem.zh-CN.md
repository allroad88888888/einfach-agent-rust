# 我建了一套 skill 激活子系统，测了它，然后删掉了 1945 行

*杀死它的那次测量，是我为了让它更好而做的。*

---

## 问题

一个托管着不断增长的能力清单的 agent 运行时，有一个 prompt 体积问题。如果每个 skill 的完整说明都待在 system prompt 里，那 prompt 就随清单一起长，而且**每一轮**你都为全部内容付钱，不管它相不相关。

显而易见的修法是惰性。给模型看一份紧凑的索引——名字加一行描述——只在需要时加载全文。

这一层今天仍然是系统在做的事。除此之外的一切都没了。

---

## 我建了什么

skill 曾经是一套**激活子系统**：

- 模型带着 skill id 调 `srv:skill/activate`
- 那会写进会话状态里的 `active_skills` 槽位
- 槽位是落盘的，于是激活这件事参与 undo、崩溃恢复和审计回放
- 之后的每一轮，组装步骤展开已激活的 skill，**把正文注入 system 段**
- `srv:skill/deactivate` 反向操作

注入需要它自己的一套机械——一个从 core 一路穿到每个 provider adapter 的 `late_system` 字段，外加各家对「这段后加的文本该放进请求的哪个位置」的分别处理。

测量就是从这里开始的。

---

## 那次让它看起来很不错的测量

不同的 provider 对「对话中途往 system prompt 里加东西」的处理差别极大。我对支持的三家（DeepSeek、Kimi、GLM）各跑了一次探针：在对话中途追加一条指令，看三件事——它到没到、模型听不听、缓存命中的代价是多少。

有意思的结果是 DeepSeek。追加一条**消息**会把它的缓存清零——哪怕插入点之前的每一个字节都没变。而把同样的文本折到**顶层 system 内容的尾部**——直觉上这应该更糟，因为你在改写 prompt 里更靠前的部分——反而保住了约 **91%** 的缓存。

于是我就照这个建了。按 provider 分注入策略：DeepSeek 上折进 system 尾部，因为实测 91%；另两家走消息级，因为那边是免费的。

这是好工程，在狭义上。我找到了一个真实的 91% vs 0% 的差异，把它编码在 provider 差异该待的 adapter 层，core 一个字节没动。

它也正是我又过了两周才发现整件事根本没必要的原因。

---

## 那次杀死它的测量

在我建我这套的同时，行业收敛到了另一个形状：把**索引**放 system prompt，而 skill **正文以普通 tool result 的形式送达**——模型调一个 `read` 工具，文本作为一条 tool result 消息进入对话。

我的第一反应是这肯定更差。正文会落在消息历史的末尾，把对话撑胖。整整齐齐地注入 system prompt，怎么想都比往对话记录里追加好几 KB 的指令干净。

然后我量了一下，推理整个反了过来。

**往消息历史的尾部追加，恰恰是 prompt 缓存明确为之而生的那件事。** 每一家的缓存都是前缀缓存。在末尾增长对话，是它们全都为之优化过的访问模式——那就是每一个正常轮次都在发生的事。而在对话中途往 system 段里注入是反过来的：它修改的是缓存区域**之前**的东西，那是这类缓存处理得最差的一种操作，而且每一家差得还各有各的样子。

我把探针预算花在了测量「每一家把我本不该做的那件事做得有多糟」上。

DeepSeek 上用 tool result 方案跑十轮——13 次 provider 调用，其中三次是读 skill 正文：

**缓存命中率 97.5%–99.8%，均值 98.5%。没有一次低于 90%，包括那几次读。**

那几次读几乎不花钱，因为它们正是缓存想要的访问模式。

---

## 删掉它长什么样

**65 个文件，+607 / −2552——净减 1945 行。** 八个文件整个删掉，连带 34 个测试。

从 core 里消失的：`activate_skill`、`deactivate_skill` 和它们的错误类型。从 provider 层消失的：`late_system` 字段、`LateSystemReshapedPrefix` 这个 adjustment 变体（以及它生成的 TypeScript）、那个代价倍数常量、两个消息组装辅助函数，还有三个 adapter 里各自的注入分支。从 runtime 里消失的：激活工具、注入路径，以及那套「因为注入内容可能和工具表撞名」而存在的遮蔽规则。

以及从探针结果里消失的：**整套按 provider 分的注入策略。** 那个 91% 的发现，我最得意的那个东西，描述的是「怎样以最不糟的方式去做一件已经没有任何理由去做的事」。

取代这一切的：两个普通工具。一个在会话开局返回索引。一个按需读正文。两个在 core 里都没有任何特判。

---

## 删不掉的那部分

有一样东西必须留下：状态 schema 里的 `SkillsActive` 槽位。

不是因为有谁读它——没有。是因为**删除之前落盘的那些会话，日志里有真实的激活条目**，而日志在恢复时要回放。把这个变体拿掉，那些会话就全部反序列化失败。

所以变体还在，标了废弃，写入路径全部移除。它是 schema 里的一个形状，存在的唯一理由是让历史保持可读。

我想把这笔交易说精确，因为它是整件事里最有意思的地方。

这套系统的核心设计主张是：agent 的全部状态活在一张带命令日志的原子依赖图里，因此 undo、redo、崩溃恢复和审计回放是同一套机制，而不是四个会各自漂移的功能。这是一个很强的性质，也是这套系统存在的大部分理由。

**这个性质的账单是：你没法悄悄地把一个状态形状撤回。** 如果你的账本是真的，它就装着真实的历史，而真实的历史会约束你。一套假装有 undo 的系统——删掉一点 UI 状态就完事——本可以干干净净地拿掉那个变体，因为它从来就没在持久地记录任何东西。

那个残留的枚举变体**就是**账本在工作。它不是债，是收据。

旁边还记着一处诚实的行为变化：一个当初激活过 skill 的老会话能正常恢复，但它的上下文里不会再有那个 skill 的正文了。状态在那儿，没人读它。这是一处真实的行为差异，被写下来了，而不是抹平过去。

---

## 我从这件事里带走什么

**一次测量有多精确，跟被测的东西该不该存在，毫无关系。** 我那个 91% vs 0% 的发现是正确的、可复现的，而且真的支撑了一个设计决策。它同时也是对一条本不该存在于系统里的代码路径的详尽刻画。

我觉得具体的陷阱是这个：**调查一样东西，会让它显得更必要。** 一旦我跑完了三家的探针、找到了一个真实的不对称、并把它编码成按 provider 分的策略，那个子系统就变成了整个代码库里我理解得最透的东西。**这跟它应该给人的感觉恰好相反。** 你测得最仔细的那些部分，正是你最舍不得删的部分——而这两件事之间没有任何理由存在关联。

真正起作用的那次测量，花了十轮和一个数字。它完全不需要理解注入那套机械——事后看，这正是那个提示。**「这东西该存在吗」通常比「我怎么把它做得更好」更便宜，而我把这两个问题的顺序答反了。**
