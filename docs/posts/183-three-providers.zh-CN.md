# DeepSeek、Kimi、GLM 到底差在哪

*实测，不是文档。这两个词都是承重的。*

---

这三家都宣称提供 OpenAI 兼容 API。三家也都确实提供了——在「一个朴素的请求能拿到合理的响应」这个意义上。差异出现在那些你只有在**已经押上一套架构之后**才会走到的地方：prompt 缓存、强制工具调用、流式里 `usage` 落在哪一帧、404 到底是什么意思。

我为了写一层 provider 抽象需要这些答案，从文档里拿不到，于是去实测。下面是测回来的东西。

**以下全部来自 2026-07-31 的真实请求**，模型是 `deepseek-v4-pro`、`kimi-k3`、`glm-5.2`，另有 08-01 和 08-03 两次追测。原始 JSON 在仓库里。数字会变，方法才是值得留下的部分。

---

## 首先：文档在两个相反的方向上都是错的

不是「不全」。是错，而且在两个方向上都错，这更糟——你连一个统一的修正都没法施加。

- **DeepSeek 的文档**说 `tool_choice` 四种取值全支持。其中两种返回 **400**。
- **GLM 的文档**说 `tool_choice` 只支持 `auto`。四种全都能用。

如果你照文档来，你会得到一个在一家上是坏的、在另一家上被白白降级的系统，而**这两种失败看起来都像是你自己的 bug**。

这个发现就是后面这一切存在的理由。

---

## 会改变你架构的那个差异

prompt 缓存分成**两种不同的匹配语义**，而这是后果最大的一条：

- **GLM 做真正的前缀树匹配。** 任何请求都会去匹配最长公共前缀，按块对齐。
- **DeepSeek 和 Kimi 只匹配扩展。** 新请求必须是它们已经见过的某个请求的严格延续。prompt 中段有任何分叉，命中率归零。

两个独立实验的结论一致。固定 system + tools，只改结尾的用户消息：GLM 首个请求就命中 5440 token，另两家命中 **0**。改写对话中段：GLM 保住 **96.7%**，另两家保住 **0**。

这对你意味着什么代价：

| | 中途改写的损失 | 一次压缩 ≈ 多少轮命中 | 兄弟 agent 共享前缀 |
|---|---|---|---|
| DeepSeek | 100% | **约 120 轮** | 没有收益 |
| Kimi | 100% | 约 10 轮 | 没有收益 |
| GLM | 约 3% | 可忽略 | 成立 |

把中间那列再读一遍。**在 DeepSeek 上，把一段对话压缩一次的代价，大约相当于 120 轮命中本来能省下的钱。** 上下文压缩是个常规功能。在 DeepSeek 上它是一个挂着 120 倍价签的常规功能，而 API 里没有任何东西会告诉你这件事。

右边那列杀掉了一个听起来很聪明的设计：「给所有兄弟 agent 同一套工具集，让它们共享缓存前缀。」那只在 GLM 上划算。另两家上收益恰好是零，所以你应该**把每个 agent 的工具裁到它真正需要的那些**。

**一处澄清，因为我一开始理解错了。** 一个冷启动的 0% 命中，看起来像是「改工具表把缓存打掉了」。把同一个请求重跑一遍，全部命中——**旧前缀从来没消失过**。零只意味着*这个变体是新的*。真实代价是那一轮全价重编码一次，之后你就在新前缀上被缓存了。**「已失效」和「还没见过」给出同一个数字，含义完全不同。**

### 工具列表在 prompt 里的位置

三家都在你改了顶层 `tools` 之后的那一轮掉到 0%。GLM 做的是真前缀匹配——所以如果 `system` 排在 `tools` **前面**，它至少应该保住 system 那几块。它没有；它也是 0。

**所以三家渲染出的 prompt 里，`tools` 都排在 `system` 之前。** 这一条我在任何地方都没找到文档，而它决定了你的缓存镜像逻辑必须采用的段序：`[tools][system][history]`。

### 小 prompt 上缓存不划算

覆盖率（`cached / prompt`）：

| prompt token 数 | DeepSeek | Kimi | GLM |
|---|---|---|---|
| ~330 | 88.5% | 77.6% | **0%** |
| ~460 | 89.2% | 54.5% | **0%** |
| ~860 | 92.8% | 89.1% | 98.1% |
| ~3100 | 97.5% | 92.4% | 99.1% |

块大小分别是 128 / 256 / 64。**GLM 在大约 860 token 以下什么都不缓存**，然后一跃到 98%。Kimi 在 470 token 时恰好缓存一个 256 块，剩下 214 个浪费掉。

**小的子 agent 不值得为前缀复用做优化**，在 GLM 上尤其如此。

## 会静默搞坏你的那个差异

Kimi 把 `usage` 放在 finish 帧**之后**的一帧里，而那一帧的 **`choices` 是空数组**：

```
data: {"choices":[{"delta":{},"finish_reason":"stop"}]}
data: {"choices":[],"usage":{"prompt_tokens":110,"cached_tokens":110,...}}
data: [DONE]
```

一个假定每帧都有 `choices[0]` 的解码器，要么 panic，要么——可能性大得多，因为大多数人会写防御性的索引访问——**静默地丢掉这一帧 usage**。

然后一切看起来都好好的。对话正常流式输出。用户拿到了答案。你只是丢掉了这家所有的 token 计数和缓存统计——也就是说你建的任何缓存回归兜底从此**永久失明，而且哪儿都不报错**。

这是整个对比里我最在意的失效形式：**响得大声的失败是便宜的。一边正常工作、一边悄悄把你的仪表盘关掉的，才是贵的。**

同一族里还有两个小一点的：

- **空内容的表达方式不一样。** DeepSeek 发一个显式的 `"content": null`；另两家直接不给这个字段。**你不能用「字段存不存在」来判断有没有内容。**
- **GLM 每一帧都重复 `role: "assistant"`。** 忽略它就没事，无脑拼接就是一堆垃圾。

## 强制工具调用跟思考模式打架

| | `none` | `required` | 指定函数 |
|---|---|---|---|
| DeepSeek（默认） | ✅ | **400** | **400** |
| DeepSeek（显式关思考） | ✅ | ✅ | ✅ |
| Kimi | ✅ | ✅ | **400** |
| GLM（开关都一样） | ✅ | ✅ | ✅ |

错误原文：DeepSeek `Thinking mode does not support this tool_choice`；Kimi `tool_choice 'specified' is incompatible with thinking enabled`。

- **DeepSeek v4-pro 默认开着思考。** 要用 `required` 或指定函数，必须在同一个请求里发 `thinking.type=disabled`。你的 adapter 可以自动这么做——但**它应该把这件事记下来**，因为它刚刚代表用户改变了模型的行为。
- **在 Kimi 上，指定具体函数是永久不可用的。** 思考常开，而且没有关闭它的字段（参数表里没有 `thinking`，且每个响应都带 `reasoning_tokens`）。能做到的最好行为是降级成 `required`，并说出来。

最后这条就是那个通用形状：**当你做不到被要求的事情时，诚实的做法是做最接近的那件，并上报这次替换。** 不是失败，也不是假装。

## 对话中途加工具

| | 通道 | 代价 |
|---|---|---|
| Kimi | 追加一条带 `tools` 的 `role:system` 消息 | **零。** 实测：prompt 5276→5382，命中仍是 5120 |
| GLM | 只能改顶层 | 一轮全价重编码，约 2 倍 |
| DeepSeek | 只能改顶层 | 一轮全价重编码，**约 120 倍** |

Kimi 是唯一有消息级工具通道的，而且免费。另两家上，对话中途改工具是一次**计价事件**。

---

## 对话中途的 system 消息：DeepSeek 是反的

后续实验（08-03）。构造一段约 4400 token 的对话，然后追加一条带新指令的 `{"role":"system"}` 消息，并与「把同样的文本折进顶层 system 内容」作对比。

| | 收下了 | 听了 | 前缀保住 | 对比重建顶层 system |
|---|---|---|---|---|
| DeepSeek | 3/3 | 3/3 | **0%** | **重建反而便宜 3968 token** |
| Kimi | 3/3 | 3/3 | 100% | 注入便宜 4352 |
| GLM | 3/3 | 3/3 | 100% | 注入便宜 4352 |

三家都收下了，三家也都听了。但 DeepSeek 会因为一条追加的 system 消息把缓存清零——**哪怕插入点之前的每一个字节都没变**——而*改写顶层 system 块*，直觉上应该更糟的那个操作，反而保住了缓存。

这跟另两家恰好相反，也跟直觉相反。

> **一条花了我一小时的方法论笔记。** 第一轮跑的时候 DeepSeek 看起来没听指令——回来的答案是空的。那不是不听：`max_tokens` 是 400，思考默认开着，314 个 token 进了 reasoning，可见的正文被截成了空。**当你在测「模型听不听指令」时，要给够 `max_tokens`，否则你测的是截断，却把它当成了行为。**

## 错误：别按状态码分类

错误体的形状是一致的——`{"error": {"message", "type", ...}}`——但状态码不是：

| | DeepSeek | Kimi | GLM |
|---|---|---|---|
| 模型名不存在 | 400 | **404** | 400 |
| key 无效 | 401 | 401 | 401 |
| 过载 | 503 | **429** | — |
| 余额不足 | **402** | — | — |

Kimi 对**不存在的模型名返回 404**，而 404 在别处通常意味着一个不可恢复的路由问题。**先按 `error.type` 分类，状态码作为兜底**，不要反过来。

**另外，给「余额不足」单独一类。** 对 402 退避重试什么也办不成，它需要立刻有人介入。把它折进你的限流桶，你造出来的就是一个永远彬彬有礼地退避下去的系统。

还有：**三家都不返回限流头。** 没有 `Retry-After`，没有 `X-RateLimit-*`，什么都没有。退避节奏得你自己定。

## 另外两件值得知道的事

**GLM 的服务端工具对你是不可见的。** 一次 `web_search` 调用返回 200，没有 `tool_calls`，没有任何搜索的痕迹，`finish_reason: stop`，也没有额外的顶层字段。它发生在模型内部。**你的 router 从来没见过它**——也就是说它进不了你的命令日志、回滚不了、没法被赋予副作用等级，并在你的审计轨迹上留下一个洞。给它建模的正确方式不是「第四种执行位置」，而是**一个会议级的开关：它拿这段对话的可审计性去换那个能力**，而且应该告诉用户这就是那笔交易。

（Kimi 的 `formulas` 是另一回事：声明成普通函数，你收到 `tool_calls` 并自己执行。可见、可审计、正常。别把这两件事混为一谈。）

**缓存写入是异步的。** 08-01 在真实使用中测到：一次紧挨着的工具调用，在上一次完成后几毫秒发出，命中了 640 而不是预期的 2304——而 640 恰好是**好几轮之前**那份镜像按块取整后的大小。下一次正常节奏的调用又回到了 97%。所以缓存摄入会滞后数秒到数十秒，而一个只跟紧邻前一个请求作比较的兜底，会在密集调用序列下**误报**。

**GLM 想得很多。** 「只回答一个词：OK」花掉 `completion_tokens: 194`，其中 191 是 reasoning。DeepSeek 在同一个 prompt 上花了 15 个。GLM 的单 token 输出价很低，但如果每一次琐碎调用都要推理两百个 token，选默认值之前请把你的实际成本重算一遍。

## 这一切最后落在哪

上面这些差异，在我当时构建的那套系统的 core 里**一条都没有出现**。它们活在 adapter 里，而 core 只陈述意图——「调这个具体的工具」「保住这段前缀」——由 adapter 决定怎么表达它，并**把任何它不得不改动的地方报回来**。

这个方向比听起来重要。它的替代方案是一个 core 会去读的能力位结构体，而那就是 `match provider` 换了层皮：N 个位就是 2^N 种组合，其中绝大多数从没执行过，而且加第四家 provider 仍然要改 core。事后上报调整，让组合数保持为一，并让每一次降级都在它发生的那一轮里可见——而不是出现在下个月的账单上。

上面这些测量就是那个设计的论据。它们几乎每一条都是这样一个地方：**API 会做一件跟你要求的不一样的事，然后什么都不告诉你。**
