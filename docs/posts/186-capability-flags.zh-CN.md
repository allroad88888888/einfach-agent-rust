# 能力位就是 `match provider` 换了层皮

*如果接第四家厂商意味着要改你的 core，那这层抽象没成。这里给一个检验，和一条出路。*

> 这是一套十二条规则里的一条。整套我写在[《不会报错的那几类 bug》](185-bugs-that-dont-fail.zh-CN.md)里了——
> 这篇是那里面最后一条的长版，因为它是唯一一条：违反它之后一直不可见，
> 直到你接第四家厂商的那天，而不是你按 undo 的那天。

---

你在支持三家 LLM provider。它们大体一致，在一些烦人的细节上不一致：一家能强制指定工具调用，一家不能；一家默认开着思考模式，而且开着的时候拒绝强制工具调用；一家什么 temperature 都收，另一家只收 `1`。

你当然知道不该在 core 里写 `match provider`。于是你抽象：

```rust
struct Capabilities {
    supports_forced_tool: bool,
    supports_named_tool: bool,
    thinking_toggleable: bool,
    temperature_adjustable: bool,
    // ...
}
```

然后 core 按位分支，不按名字分支。厂商名现在只出现在一个地方了。那感觉上是对的形状，而且每一次 code review 都会通过它。

我想论证它是同一个错误，只是礼貌一些；并给你一个问题，问完就知道自己在线的哪一边。

---

## 那个检验

> **接第四家 provider 的时候，你要不要改 core？**

用能力位，要——而且不是因为疏忽。是结构性的。

新那家带来一个现有 provider 都没有过的位组合。比如 `supports_named_tool: false` 配上 `thinking_toggleable: true`，而你现有的三家只产生过 `false/false` 和 `true/true` 这两对。这个组合现在会走一条你 core 里**从未执行过**的路径。

四个位是十六种组合。六个位是六十四种。你有三家 provider，所以你最多测过其中三种，而且你是靠跑它们才知道是哪三种的。

**能力位没有消除分支。** 它把厂商**名字**从分支里拿掉了，于是更难看出你到底在按谁分支——同时让人感觉问题解决了，而实际上分支数还变多了。

还有第二个症状，如果你留意的话它出现得更早：**你会不停地加位。** 每接一家都冒出一个新的差异点，每一次添加单独看都站得住，而组合空间每次翻倍。**一个每接一家厂商就长一个字段的结构体，不是对厂商的抽象——它就是那份厂商清单，转置了一下。**

---

## 把方向反过来

替代方案是：别再事先问了。

**之前**：core 问「你能强制指定工具调用吗」，然后按答案分支。

**之后**：core 说「这一轮必须调 `fs/read`」。adapter 尽力而为。做不到那件事的话，它做最接近的那件，然后**把这次替换的记录附在响应上**。

```
Adjustment::ToolChoiceDowngraded { wanted: "fs/read", used: "required" }
Adjustment::ThinkingDisabledForToolChoice
Adjustment::TemperatureOverridden { wanted: 0.0, used: 1.0 }
```

core 只有一条路径。它发出意图、拿到响应，然后——因为反正它也躲不掉——检查一下它想要的事情是不是真的发生了。

最后这个从句才是整件事成立的原因，而且它很容易被一眼扫过去。**强制工具调用在任何一家都不是保证。** 就算 API 收下了你的 `tool_choice` 一声不吭，模型也可能回别的东西。所以 core **本来就需要**那条「验结果」的路径。它已经存在、已经被测、每一轮都在跑。

一旦你有了那条路径，事前的能力检查就什么都没买到。它是同一个问题的第二套、更不可靠的答案——还额外背了一个缺点：它是**事前**用一份静态的 provider 描述回答的，而不是**事后**用真回来的东西回答的。

---

## 具体买到了什么

**要测的组合从 2^N 变成 1。** core 只有一条路径。provider 相关的行为活在各个 adapter 里，每个都是纯函数，可以拿录下来的响应帧去测，不联网。

**加一家 provider 不碰 core。** 新目录、四个函数、完事。这正是这层抽象本该交付的性质，而能力位版本没交付。

**降级变得可见。** 这一条如果我没亲眼见它起作用，大概会低估。

用能力位，core 悄悄走了较弱的那条路。没什么不对；也没有任何报告；行为只是跟别处不一样了，而且系统里没有任何一处产物在说这件事。半年后有人问「为什么这个在 A 家能用在 B 家不行」，答案是某处一个没人看过的布尔值。

用 adjustment，每一次替换都是**附在它发生的那一轮上的一份数据**。它进日志、进 CLI 输出、进审计轨迹。「这一轮的强制工具调用被降级成了 `required`，因为这家关不掉思考模式」——这是系统能够关于自己说出的一句话。

而且它给你一条值得明说的性质：**adjustment 列表为空，意味着这次请求是按预期执行的。** 这是个很强的断言，而它之所以能成立，只是因为 adapter 有义务上报，而不是有权决定。

这就指向了这个设计真正在防的失效形式：**一次静默的妥协。** 不是「我们做不到」——那没关系，那是诚实的。而是「我们做了别的，谁也没告诉」——那正是能力位分支从构造上必然产生的东西，因为分支是在「还没有一轮可供附着任何东西」之前就走掉的。

---

## 线到底划在哪

「provider 相关的东西放 adapter」太虚，落不了地。两条规则把它变具体。

**请求组装归 adapter，不归 core。** core 只供料——system 块、消息历史、工具规格、意图——不合并、不成形。由 adapter 组装。这不是审美偏好：每一个组装决策都依赖一个厂商差异（晚加的工具放哪、thinking 字段进不进缓存前缀、temperature 到底能不能设）。在 core 里组装，意味着你要写一个「做这些决策但不许知道任何事」的函数——也就是它做不了这些决策——也就是它只是个搬运工。

**但 adapter 无权改变世界。** 它们是纯函数。而正是这条约束，决定了那些真正难分的情况。

拿上下文压缩来说——对话接近窗口上限时丢掉旧轮次。三个子问题，三个不同的答案：

- **何时压缩**——core。这是算术：token 数对配置的窗口大小。没有厂商分支，只有一个参数。（**参数没问题。这条规则禁的是按厂商行为分支，不是禁接受一个随厂商而异的数字。**）
- **怎么压缩**——core。压缩是一次状态变更；它必须走命令层，才能跟别的一切一样进 undo 日志。
- **压完的结果在请求里怎么摆**——adapter。一家做真正的前缀树匹配、能保住一条共享分支；另两家只匹配扩展，编辑点之后的全丢，于是它们吃下这个代价并报一条 adjustment。

第三个才是有意思的那一刀，而它必须这么分的理由是：**如果 adapter 自己压了，prompt 和记录下来的状态就对不上了。** undo、审计、缓存前缀镜像，全都会在描述一场从未发出去过的对话。**adapter 有权决定怎么呈现这个世界。它无权改变这个世界。**

那条线就是这个：**adapter 翻译，不改写。** 其余一切由此而来。

---

## 诚实的代价

两条，都不免费。

**你是事后才知道的。** 能力检查在你花钱之前就失败了。adjustment 是在一次你已经付过钱的请求之后到达的。当那次替换是你本来宁可完全避开的事情时，你是花钱买了这个消息。

我仍然认为这笔交易划算，因为事前检查的好坏，完全取决于你那份关于 provider 的静态描述——而以我实测的经验，**厂商文档在两个相反的方向上都错**。我见过文档说支持四种取值、实际拒掉两种的 API，也见过文档说只支持一种、实际四种全收的 API。**能力位是一句你手工维护、从不验证的、关于某家 provider 的断言；adjustment 是一次真实发生过的请求的观测。**

**得有人去看 adjustment。** 它们是数据，而没人读的数据比一个分支更糟——分支好歹还干活。如果它们只落进一个日志文件，那你造出来的是一套非常整洁的、用来忽略问题的机制。它们需要浮到人看得见的地方——轮次输出里、状态视图里，某个有眼睛盯着的地方。

---

## 一句话版

如果你的 provider 抽象里有一个布尔结构体、而 core 会去读它：数一数组合数，数一数你实际跑过几种，然后问一句第四家来的时候会发生什么。

然后试试那个反转：**陈述意图，让 adapter 去替换，并要求它说出来。** 一条路径，一种测试组合，而每一次妥协都变成它发生的那一轮里的一个可见事件——而不是一个从添加那天起就没人再读过的布尔值。
