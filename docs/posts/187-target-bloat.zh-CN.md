# 267 个测试文件、58 GB 的 `target/`，以及那个没撑住的修复

*一个 Rust 构建膨胀的故事，两半。前一半是所有人都会讲的那个。后一半才是值得读的。*

---

## 上半场：你听过的那个故事

一个 Rust 项目开工两天，构建变慢了。不是「我去倒杯咖啡」那种慢——是 `rustc` 打印出任何东西之前，先干等好几分钟。

`du -sh target/` 说 **58 GB**。`find target -type f | wc -l` 说 **88 万个文件**。

这个项目有 12.8 万行 Rust，存在了 48 小时。

### 原因

`tests/` 目录下**直接**放着的每个 `.rs` 文件，都是一个独立的 crate。Cargo 会把它编成一个独立的二进制，而每个二进制都要链接整棵依赖树。

那里有 267 个。

267 次独立链接、267 份共享依赖代码的拷贝、267 套调试信息——而这套测试本来可以是一个二进制。

第二个因素是文件**数量**，不是体积。`rustc` 启动时会枚举 `target/debug/deps`。几千个条目时这是免费的，几十万个时就不是了：**构建之所以慢，是因为之前的构建留下的东西太多。**

### 修法

两处改动。

**每个 crate 一个测试 harness。** 不再是 `tests/foo.rs`、`tests/bar.rs`……而是全部放进 `tests/it/`，只留一个 `tests/it/main.rs`：

```rust
//! 本 crate 的单一集成测试 harness：所有用例编进同一个二进制。
//! 为什么合并：267 个单文件测试 = 267 个链接产物 + 267 次进程启动。
//! 加测试 = 在 tests/it/ 下建文件，然后在这里加一行 `mod`。

mod cancel;
mod undo_redo_roundtrip;
mod snapshot_recovery;
// ...
```

加一个测试现在是「建文件、加一行」。一次提交挪了 296 个文件。

**别再生成完整调试信息。** panic 栈需要的是行号，不是完整的类型信息。第三方 crate 连行号都不需要——你不会去单步跟进它们：

```toml
[profile.dev]
debug = "line-tables-only"

[profile.dev.package."*"]
debug = false
```

构建又快了——今天改动最底层那个 crate 里的一个文件、重建整个 workspace，**6 秒**。事故写进了项目的贡献者文档，免得有人再造一次。结案。

## 下半场：八天之后

我又去量了一次 `target/`——想给这篇文章拿一个干净的前后对比数字。

```
target/debug/incremental   16 GB     ← 最大
target/debug/deps          14 GB
target/debug/examples     688 MB
─────────────────────────────────
target/                    31 GB / 794,507 个文件
```

31 GB。将近 80 万个文件。**我准备拿来当「修复之后」的数字，几乎就是当年的「修复之前」。**

但看它在**哪儿**。`deps`——那次修复瞄准的东西——是 14 GB，已经不是最大的一块了。修复是有效的。是别的东西长进了它腾出来的空间。

`incremental/` 里有 **708 个会话目录**，最大的单个 151 MB。

增量编译状态是按 crate **和**编译配置分的。这个项目的配置比多数项目多：一个 `ts` feature、`--all-targets`、三个编译目标。每种组合各有一份增量状态，而每一份都留着历史。

我把它删了。释放 16 GB，`target/` 降到 15 GB，然后我开始写这一节。

### 然后有人问，为什么还有 15 GB

问得好。其中 `deps/` 占 14 GB。拆开看：

| | |
|---|---|
| `.rlib`——真正的构建产物 | 1.7 GB |
| `.rmeta` | 906 MB |
| **`.rcgu.o`——中间目标文件** | **约 11.4 GB，631,526 个文件** |

`.rcgu.o` 是每个 codegen unit 一个目标文件。dev profile 默认 256 个 codegen unit，而**每一个不同的 build hash 各有一整套**——**Cargo 从不回收那些已经不是当前 hash 的套件。**

有一个 crate，`agent_cli`，攒了 **40 个 build hash、42,732 个目标文件**。40 个里有 1 个是活的。另外 39 个是我过去两周跑过的构建留下的沉积物。

目标文件是一次**已经完成**的链接步骤的输入，旁边那个 `.rlib` 就是它的结果。删掉它们，最坏的代价是下次构建重新生成一遍。

所以：incremental 不是最大的那个。它是**最好认的**那个——一个目录，名字明确，用途明确。真正更大的问题是 631,526 个机器生成名字的文件，没有任何工具会主动把它们摆到我面前。

最终状态，横跨本仓四个 workspace：**35 GB → 9 GB**，`deps/` 从 **631,526 个文件降到 3,227 个**——大约 200 倍。

后面那个数字才是要紧的。`rustc` 启动时枚举 `deps/`。让构建变慢的从一开始就是文件**数量**，不是体积。

整个过程里没有任何人做错过任何事。没有第二次失误。磁盘是在正常工作中被填满的，两次，在两个不同的地方。

## 我真正从这件事里带走的

**教训不是「注意你的测试文件布局」。** 那是表层原因，修它是对的——`deps` 确实**因为那个原因**不再是问题了。

教训是：**`target/` 是一个没有淘汰策略、没有预算的缓存**，而一个针对某一个增长来源的修复，不改变这个性质。我精确、彻底地修好了一个症状，认真写了记录，然后原封不动地留下了底层性质：**系统里没有任何东西对「`target/` 该有多大」持有意见。**

还有一个更锋利的版本，那才是我希望有人带走的部分。

**我发现那 16 GB，是因为它有名字。** `incremental/` 是一个目录，它有含义，而且它出现在 `du -sh target/debug/*` 的最上面。紧挨着它的那 11.4 GB，是 631,526 个叫做 `agent_cli-06e2d0425d1d64a9.2te8wc0c7sgg9x7bhuy3qs9pn.0bq0m75.rcgu.o` 之类的文件——它之所以浮出来，只是因为第二个人看了我公布的数字，问了一句「怎么还这么大」。

**可辨识度和体积不相关。** 容易注意到的东西，不是最大的东西——而如果你唯一的发现机制是「早晚有人会看一眼」，那你会找到那个好认的问题，然后就停下来。

所以我真正需要的修复，从来不是「重组测试」，也不是「删掉 `incremental/`」。是**一个会被定期检查的数字**——让「`target/` 现在多大」变成有东西自己会去问的问题，而不是八天后我写博客时偶然撞见、而且只答了一半的问题。

这就是「修好一次事故」和「修好产生事故的那个东西」之间的差别。前者我已经做了两次，后者我还没做完。

## 如果你只想要那几个便宜的收益

它们是真的，两分钟的活，而且确实有用：

1. **每个 crate 一个测试 harness。** `tests/it/main.rs` 加 `mod` 行。在你有 267 个文件**之前**做，不是之后。
2. **`debug = "line-tables-only"`**，以及给 `[profile.dev.package."*"]` 设 `debug = false`。panic 栈依然可读。
3. **真的去量**：`du -sh target/` 和 `find target -type f | wc -l`。让人吃惊的是文件数那个——而且在磁盘被填满之前，先让 `rustc` 变慢的也是它。

然后，装一个替你检查这个数字的东西。那部分我到现在还没补上。
